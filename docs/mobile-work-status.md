# Mobile work status (0.8.9)

`GET /api/mobile/work-status` is a read-only, authenticated Worker endpoint. It uses the normal `Authorization: Bearer <session>` and device/IP checks. The current role is independently checked against the active `app_users` row; a modified role claim is rejected. No client-supplied username, role or tenant is accepted. Auth/role failures return 401; inability to verify the account returns 503. No mutations, report submissions, tracker comments, or issue creation occur here. Existing `/api/reports` receipts are unchanged.

## Isolation and coverage

This is for **one tenant per D1 database** only, as assumed by the existing stock schema; it must not be used with tenants sharing a D1 database. Each account sees only its own stock-adjustment requests, even if it is an approver. These historical stock records are keyed by username, so access requires a valid current `app_users.created_at` and includes only records with a server-stored timestamp **strictly later** than that time. Same-second and older records are omitted. It relies on trustworthy, monotonic timestamps and intact creation dates; imports or restores can invalidate those assumptions. The environment owner has no account lifetime and gets `OWNERSHIP_UNVERIFIABLE` for stock requests.

New report submissions attempt to bind the report to the authenticated, non-reused `app_users.id` or the environment owner slot before GitHub delivery. Bindings are best-effort: if verification or storage fails, no ID is guessed and older username/timestamp filtering still applies to unbound non-owner reports. Legacy and unbound reports therefore retain the timestamp limitations above; owner reports without a binding are omitted. The app's normal account creation uses AUTOINCREMENT IDs; imports or database restores that reuse IDs can break isolation. The owner slot represents the configured environment owner, not a historical individual. The application-level backup and D1 migration-copy tools do not preserve these bindings; use a database-level backup to retain them. Absence from a list is not evidence that a record does not exist.

`mobile_actions` are excluded because their creator is client-supplied and they lack reliable ownership/update timestamps. User-report delivery status is not a tracker issue status. Crash reports, unrelated GitHub issues, Linear projects and other work types are not available. This endpoint cannot be used to infer that any of those categories are clear.

With the existing report GitHub configuration, work status automatically verifies the configured repository is public and reads linked issues anonymously; the server token is never sent on these reads. If the repository is private, unreachable or no longer public, this mode returns unavailable. Set `WORK_STATUS_GITHUB_ENABLED=false` to disable GitHub reads. A private repository requires explicit `WORK_STATUS_GITHUB_ENABLED=true`, only after ensuring its issue titles/state may be disclosed to each report submitter and that the ownership assumptions above hold. In this mode the server token is used. No client receives credentials, issue bodies or comments. Only linked report issues are fetched, not the repository's issue list. Links must match `https://github.com/<configured-owner>/<configured-repo>/issues/<number>` exactly, as must GitHub's response. A changed repository, invalid link, missing table, forbidden/deleted issue, malformed response, timeout, or upstream error makes the GitHub source unavailable for that page. Linear is always unavailable: a Linear connector in a developer's tool session is not a deployed integration.

## Query and pagination

Optional `limit` is an integer 1–5 (default 5), applied independently per source. Optional `in_app_cursor` and `github_cursor` are positive decimal IDs previously supplied as that source's `next_cursor`. Unknown, repeated or malformed parameters return 400 `INVALID_QUERY`. Records are ordered by their local table ID descending, using keyset pagination. Send each returned cursor independently; `null` means no further page for that source. GitHub cursors are local report IDs, not GitHub issue numbers. Pagination is not a snapshot; new records appear on a fresh first page, and deletes/updates may change later pages. A source error yields no next cursor; retry the same input cursor, not a new one.

## Response

A successful HTTP 200 response has `success: true`, `in_app`, and `trackers.github` / `trackers.linear`. Each source has `availability` (`available` or `unavailable`), `synced_at` (UTC time the page was successfully read, otherwise null), `items`, `next_cursor` and `error` (null or a machine-readable code). An unavailable source has an empty items array, **not** an all-clear assertion. `NOT_CONFIGURED` means disabled/missing tracker configuration; `NO_LINKED_REPORTS` means there were no linked report issues on this page, so no issue was read and tracker health is unknown (the public repository check may have been contacted); `OWNERSHIP_UNVERIFIABLE` means ownership could not be verified; `SOURCE_UNAVAILABLE` means a data, validation or upstream failure. A GitHub failure never hides the independently fetched in-app page. No stale cached tracker data is served.

Each item contains `source`, string `id`, `title` (nullable for an unnamed stock product), `status`, and `updated_at`. A stock ID is `stock_adjustment_requests.id`; its title is the stored product name and status is the stored workflow status (`pending`, `approved`, `rejected` as currently implemented), not a synthesized progress state. `updated_at` is null because the table lacks a reliable general update timestamp, including reopened requests. GitHub IDs are issue numbers, statuses are GitHub's exact `open`/`closed` state, timestamps are GitHub `updated_at`, and `url` is the validated HTTPS issue link. Titles are length-limited and secret-redacted. Nothing is inferred from labels or report-delivery status. Do not display a null update time as a known fresh timestamp.

Responses set `Cache-Control: no-store` and `CDN-Cache-Control: no-store`; no per-user data is cached. The existing Worker rate limiter applies 30 requests/minute per account per isolate and returns 429 with `Retry-After`; it is best-effort, not a distributed quota. GitHub requests are bounded to at most five concurrent issue reads per page, 4 seconds each and 64 KiB per response; no automatic retry is performed. Errors are deliberately generic and do not log credentials, issue bodies, report text or upstream responses. Auth and account checks use a primary D1 session where supported.
