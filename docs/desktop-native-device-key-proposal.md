# Desktop device-key protocol proposal v0.1 (not implemented)

This is a **proposal for security review**, not an active capability, promised wire contract, attestation scheme or permission to deploy. A strict cryptographic verification primitive is implemented in `worker/lib/desktop-device-proof.ts`, but it is unwired and does not consume nonces or prevent replay; it is intentionally a narrower profile than generic DPoP. The existing staging pilot issues bearer tokens and does not enforce any of the proof requirements below. No endpoint or flag below exists. Review the binding, throughput, recovery and OS integration before choosing it. See the [cross-platform audit](desktop-native-cross-platform-audit.md).

## Candidate profile

Use OAuth DPoP-style compact JWS proofs (RFC 9449) with ES256 / ECDSA P-256 and RFC 7638 JWK thumbprints. TLS certificate verification remains mandatory. A key identifies possession of a private key, **not** a person, trusted application, uncompromised device, or TPM. A desktop creates one key pair per installation and server origin; only the public key crosses the network. Derive its thumbprint from the canonical public JWK. Do not use self-declared fingerprints, hardware claims or Turnstile as authentication.

Proposal assumes an exact canonical HTTPS origin, including non-default port, and a dedicated `/api/auth/desktop/v3` namespace. For discussion only, the nonce endpoint could be `POST /api/auth/desktop/v3/nonce` with JSON `{ "origin":"https://test.example:8443", "purpose":"enroll"|"refresh"|"logout"|"resource" }`. A successful response could be `{ "success":true, "data":{ "nonce":"<base64url 32 random bytes>", "expires_in":60 } }`; no user existence should be revealed. Nonces are scoped to exact origin and purpose, CSPRNG-generated, held server-side by hash, expire after 60 seconds, and consumed once. Nonce issuance needs its own broad persistent IP and deployment quotas, bounded response/body/time, cleanup and fail-closed storage; do not use a user-selected or self-signed nonce. Exact 60-second timing is a candidate to test, not a deployed promise.

Every proof is one compact JWS supplied as the `DPoP` header:

```json
{"typ":"dpop+jwt","alg":"ES256","jwk":{"kty":"EC","crv":"P-256","x":"<32-byte-base64url>","y":"<32-byte-base64url>"}}
{"jti":"<random unique base64url>","htm":"POST","htu":"https://test.example:8443/api/auth/desktop/v3/login/otp","iat":1700000000,"nonce":"<server nonce>","atlas_txn":"<request_id>"}
```

The signature is 64-byte fixed-width `r || s` as required by JOSE ES256, not ASN.1 DER. `htm` is the actual uppercase HTTP method; `htu` is the actual externally visible canonical HTTPS target URI without query or fragment, per DPoP. Normalize/compare with a URL parser and preserve effective port. Reject forwarding-header origin spoofing, redirects, duplicate JSON fields, invalid UTF-8/JWK points, private JWK fields, wrong curve, wrong algorithm, malformed signature and wrong `typ`. `iat` is integer UTC seconds; proposed acceptance window is ±60 seconds and nonce expiry is independent. `jti` is at least 128 CSPRNG bits and unique for that key; reject duplicate `(key thumbprint,jti)` for the replay window, across all Workers. Ignore client clocks for the server's expiry authority. An `atlas_txn` claim is an application extension for the enrollment/OTP flow: it must equal the server-side request ID; it is not part of generic DPoP.

For a protected business request, the proof uses that request's method and URL and additionally `"ath":"<base64url SHA-256 of the ASCII access token>"`; the HTTP header is `Authorization: DPoP <access_token>`. Reject a missing, substituted or wrong-origin token, wrong `ath`, mismatched key thumbprint or a bearer-only attempt. The server's stored session binds the token hash and thumbprint to account, exact origin, key and revocation status; it must validate the same proof at **every** authenticated Worker gate, including uploads, reports and secondary routers. Do not use a header such as `X-Device-Fingerprint` as a substitute. Query strings and arbitrary request bodies are not signed by standard DPoP; assess transaction integrity and proxy canonicalization separately, especially streaming uploads.

For issuance after the existing server-verified challenge, native password and OTP, the OTP POST carries the proof and `atlas_txn` matching the proof-bound transaction. The same D1 transaction must consume the valid OTP, nonce and proof ID, register the public-key thumbprint and create the session family. Neither the key nor the access/refresh token enters the WebView. The response would include the normal token pair, `token_type:"DPoP"`, expiry, exact origin and a non-secret `device_id`; the refresh family is bound server-side to that same key thumbprint. Registration cannot be based on a public key alone. If the OTP or issuance response is lost, do not replay; cancel/restart and provide authorized orphan-session revocation.

A proposed `POST /session/refresh` JSON `{origin,refresh_token}` carries a fresh `DPoP` proof bound to that exact method/URL, purpose `refresh` and the enrolled key. Refresh tokens are not access tokens, so do not invent an `ath` claim for them; lookup the refresh hash and compare its stored thumbprint to the proof key. Atomically consume nonce and jti, record the old refresh hash, compare-and-swap the family and return **both** new tokens. Concurrent reuse or any historical refresh reuse revokes the whole family. A lost response must not be retried; attempt an authenticated best-effort logout using the last held token plus a fresh proof, then clear local material and reauthenticate. A proposed `POST /session/logout` with the same JSON and a fresh `logout` proof can revoke on current or retained old refresh; a lost logout response does not establish server revocation. Token and proof replay, rotation, account/role/credential change, mailbox change and key/device revocation must be atomic with session authority on the primary.

Proof nonce/JTI claim and the state-changing action must be atomic: a nonce check followed by a separate mutation is raceable. A resource request's proof may be consumed even when the business operation fails; do not retry that proof. A fresh proof is needed for each concurrent request. Infrastructure must bound nonce issuance, replay-table writes and retention and handle D1/clock outage fail-closed; this extra write per request can be expensive. Standard DPoP interoperability, nonce challenges, capacity and all error/retry behavior need review and real-client testing before implementation.

## Key replacement, revocation and recovery

Proposed device records have a random non-secret device ID, account ID, origin, JWK thumbprint, state and creation/revocation timestamps; no private key. Replacing a key requires a new fully authenticated password + verified-mailbox OTP ceremony and a proof from the new key. Existing-key authorization and notification could additionally be required; select policy before allowing replacement. An authorized account-management or administrator action must revoke a specific device and all its token families transactionally, with secret-free audit and authorization checks. Account disablement, deletion and approved factor reset revoke affected devices and families. Never reactivate a revoked key simply because a matching public key returns. A lost key must not fall back to fingerprint or bearer login; use an explicitly approved recovery path and audit/notify the event. Orphan sessions and already-authorized in-flight requests need operational handling. No recovery or device-management endpoint is implemented.

## Windows 10/11 and Rust implementation work

A possible implementation uses Windows CNG key storage APIs and an ECDSA P-256 signing key generated under `Microsoft Platform Crypto Provider` when available, with export disabled; use `Microsoft Software Key Storage Provider` as a proposed fallback where permitted. The CNG public ECC blob must be converted to fixed-width P-256 coordinates and base64url JWK. Convert the CNG signature representation to the JOSE 64-byte `r || s` representation as needed; test against the Worker verifier and known standards vectors. Use per-user ACLs and OS-protected key references; remember that local processes running as that user may still request signatures. Persist atomically in an OS vault: exact origin, account identifier, device ID, key-container reference, access/refresh pair, expiries and schema version. Never persist OTP, password, PKCE verifier beyond the in-flight request, provider token or a private-key export.

A client assertion that it used the Platform provider or a non-exportable flag is **not verified TPM attestation**. A server can claim hardware-backed protection only after verifying an appropriate attestation chain, key binding and policy against trusted roots, with lifecycle/revocation and privacy review. Neither such verification nor an attestation policy exists here. Windows editions, TPM provisioning, remote desktops, roaming profiles, key cleanup, software fallback and repair require real Windows 10/11 tests. User approval is required before making TPM mandatory or selecting lost-key recovery. The desktop also needs the challenge-only isolated WebView, explicit browser fallback and native password/OTP described by the [implemented staging contract](desktop-native-auth-v2-client.md); Discord-like presentation says nothing about provider or runtime compatibility.
