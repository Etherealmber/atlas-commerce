# JournalBuffer Actors migration experiment (local only)

## Scope and current result

This is a prototype for the existing JournalBuffer, not a production deployment. The production Worker still exports the current class and uses the existing `JOURNAL_BUFFER` binding and `journal-v1` object name. `@cloudflare/actors` is pinned as a development dependency, and the experimental adapter is not imported by the production Worker. No production database, R2 bucket, secret, or object was accessed.

Run `npm ci && npm run test:actors-journal`. This uses a temporary local Miniflare/workerd instance with an isolated local R2 bucket solely as a deterministic delivery test double. It exercises the existing class, swaps the local script to an Actors subclass **with the same class name and namespace**, then rolls back to the original class. It checks preservation of one queued ciphertext, a pending native alarm, duplicate/conflicting enqueue semantics, and successful delivery after rollback; it separately tests an alarm firing while the adapter is active. It is not a Supabase integration or proof of Cloudflare production upgrade/rollback behavior.

The adapter delegates `fetch` and native `alarm` to the existing implementation. This intentionally preserves the storage keys, encryption, queue batching, idempotency and alarm scheduling. It does **not** yet replace those with typed Actors RPC, `@Persist`, multi-alarms or the retry helper; it is only the first compatibility step. The Actors beta constructor adds library-owned SQLite state and initialization, so the production implications need review. The default Actor request handler also waits for `setName`, unlike our existing DO protocol, so this adapter intentionally overrides it. The Actors multi-alarm scheduler and the existing native alarm both control the one DO alarm; enabling both without a design could delay or overwrite journal retries. Do not add the multi-alarm helper to this object until their interoperability and rollback are proven.

## Required before proposing production migration

1. Resolve the current live Supabase/queue failures first. Verify schema, server-only credentials, 30-day retention and actual queue delivery; do not expose secrets.
2. In a separate Cloudflare staging account/environment with separate bindings, encryption key, database and no production traffic, test the adapter against a dedicated Supabase project. Test backlog, lost acknowledgements, retryable and nonretryable failures, batching, concurrency, restarts/evictions, alarm scheduling and upgrades/rollbacks with pending items. Monitor latency, error rates, costs, data retention and queue counts.
3. Inspect beta library initialization, SQLite tables and alarm ownership with real staging data. Confirm existing encrypted records, cursor, diagnostic state, original object namespace and scheduled alarm survive the intended deployment strategy. Verify no duplicates or lost records. Test multi-alarm and backoff separately; a helper that catches a callback error may not preserve the existing retry contract.
4. Design a reproducible backup/export and restoration procedure for pending entries and scheduled alarms. Retain the exact journal encryption key while any entries are pending. Agree on cutover metrics, rollback conditions, and how to handle concurrent writes, gradual deployment and lost acknowledgements. Obtain explicit approval before any production deployment or binding/class migration.

Do not rename, delete, recreate, or merge the production binding/object. Do not run Actors tools against production. Source history in D1/R2 is unchanged; Supabase remains the journal destination. This experiment does not reduce Durable Object usage, fix existing Supabase errors, or guarantee delivery.
