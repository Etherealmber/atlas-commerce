# Mobile product and movement actors (0.8.9)

Authenticated product detail (`GET /api/products/:id`), list (including `?fields=mobile`), variant list, and barcode lookup provide `created_by` and `approved_by` as usernames or `null`. Direct product creation (`POST /api/products`), variant creation and scan quick-product creation record the authenticated creator. Request-supplied actor fields are ignored. There is no server-backed product approval identity in these creation paths, so `approved_by` is `null`, not the creator or a guessed approver. Agent-created products and older rows without reliable metadata also return `null`.

`GET /api/products/:id/movements` and `GET /api/stock/movements` expose the same actor fields. `created_by` is the stored movement actor, not necessarily the person who requested a stock change. Newly approved stock-adjustment requests record the signed-in decision maker as both movement creator and `approved_by`. Direct/unapproved movements have no approver. Mobile-handoff stock writes now use the authenticated session for the movement creator rather than the caller's `completed_by` string; other audited scan stock operations, invoice stock changes, transfers, counts and purchase receipts use their session when available. Automated jobs and other workflows without a trusted actor remain unknown. Existing movement data was written by multiple older workflows, some with client-supplied names, and cannot be assumed to be verified. Empty or missing identities are `null`; no historical names or approvals are inferred.

`migrations/0010_inventory_actor_columns.sql` is a no-op marker like migration 0008: PRAGMA-aware runtime helpers lazily add nullable metadata columns on new product creation or stock approval, tolerating schemas where some columns already exist. Reads work before the columns exist and return `null` where data is unavailable. The original `created_by` movement field and all existing history are retained. If a deployment cannot alter its schema, the optional metadata may remain unavailable; normal stock writes continue on the legacy schema when possible. The change does not add a product approval workflow or change the authorization policy for existing workflows.

## Related mobile integrations

`POST /api/reports` and `GET /api/mobile/work-status` already handle GitHub report creation and linked issue status with server-side credentials; see [mobile work status](mobile-work-status.md) for automatic public-repository reads, private-repository opt-in, URL validation and ownership limitations. New reports can be bound to the environment-defined owner slot. `GET`/`PUT /api/mobile/snake-score` already provide private, monotonic account scores; see [Snake score](mobile-snake-score.md). Its score table is automatically initialized when needed. No deployment or credentials are included in this change.
