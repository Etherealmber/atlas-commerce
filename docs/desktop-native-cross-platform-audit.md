# Native desktop: cross-platform implementation audit (PR #193)

## Status and security boundary

Production native authentication is **not implemented or advertised**. No production discovery capability, enrollment/recovery endpoint, device-key nonce endpoint or DPoP-bound session exists. The present v2 password/OTP pilot remains explicitly staging-only with one test account and test mailbox. Ordinary website authentication and presentation are unchanged. See [staging client wire contract](desktop-native-auth-v2-client.md), [mailbox alternatives](desktop-native-enrollment-options.md), and [proposed device-key v0.1](desktop-native-device-key-proposal.md). Production flags must remain absent/disabled; no setting in this change enables production. Preview bindings in `wrangler.jsonc` share production resources, so do not test this branch there against live data.

The staging browser validates Turnstile directly with Cloudflare Siteverify and native polling is transaction/proof bound. The proof-of-concept tokens are **bearer** tokens; they are not protected by the new candidate device proof verifier. Existing refresh replay/logout/race tests do not prove safety of a future key-bound production session. Do not apply v3 design claims to v2.

## Changes from this audit

`desktop-mail-transport.ts` implements an opt-in `resend-v1` multi-recipient-capable transport, one intended recipient per message, using only the fixed `https://api.resend.com/emails` endpoint and a separate native API key and sender. `createConfiguredNativeMailbox` joins that real transport to the existing enrollment core **only when a caller supplies an explicit authorization adapter**; there is no caller in the Worker and no route. No current account or mailbox was changed. In integration tests, fetch is mocked and the authorization policy is simulated, not a real Resend or authorization test. The transport never falls back to the company's shared mailbox or the restricted Cloudflare EMAIL binding. Its provider acceptance status is not evidence of delivery. Timeout/abort does not guarantee the provider never accepted an already-transmitted message. A verified sender domain, an account with recipient delivery, provider credentials, policies and actual delivery/bounce monitoring are required. Provider operators may see the address and code; do not log request/response bodies. Secrets are not supplied here.

Configuration proposed for future integration only: `DESKTOP_NATIVE_MAIL_TRANSPORT=resend-v1`, `DESKTOP_NATIVE_RESEND_API_KEY` as a separately scoped secret, `DESKTOP_NATIVE_MAIL_FROM` as a verified bare sender address, and `DESKTOP_NATIVE_MAILBOX_MAC_KEY` as a separately generated high-entropy secret. Missing/invalid settings fail closed. Configuring them alone does not activate a route or production feature. Before activation, review provider terms, region/data retention, DMARC/SPF/DKIM, access controls and logging; simulate disabled API, timeout, bounce, delayed and duplicate mail. Key rotation strategy is not implemented; replacing the MAC key invalidates pending codes. Never set these secrets via committed configuration or logs.

`desktop-device-proof.ts` implements a bounded, strict v0.1 candidate ES256 JWS verification primitive: duplicate JSON keys, private JWK data, unsupported fields/algorithms, malformed encoding, invalid curves/signatures and mismatched method, URI, nonce, time, key, token hash or transaction are rejected; an RFC 7638 thumbprint is returned. Its strict allowed claim/header profile is intentionally narrower than general RFC 9449 interoperability and must be versioned and tested with the eventual Rust client. The expected URL, nonce and binding **must** be derived from authoritative server state, not from the proof. This function does **not** issue nonces, consume them, stop replay, authorize actions, create sessions or validate attestation. It is not called by any Worker route; a valid proof can be verified repeatedly. Add no production route until nonce and jti consumption are atomic with the protected action, and the binding is enforced on every protected entry point including reports, uploads and query-token exceptions.

## Integration blockers and required decisions

1. Choose first-enrollment authority: (A) existing session + explicit password reauthentication + new-mailbox code, recognizing a session-and-password thief can enroll; or (B) an independently verified administrator/out-of-band approval plus new-mailbox proof, recognizing operator and social-engineering risk. The owner is configured separately from `app_users`; design a distinct stable owner identity without conflating the owner with a secondary admin. Choose old-mailbox confirmation/notice requirements and a process for addresses that cannot receive them.
2. Choose lost-mailbox/key recovery: (A) another previously enrolled strong factor or trusted device, with fresh proof and notification; or (B) verified staffed/dual-control recovery, notification and optional cooling-off, with native factor and session revocation. For the owner choose either pre-enrolled offline single-use recovery material or independently verified multi-person break-glass. Decide approvers, evidence, delays, audit and revocation scope. Neither path currently exists; no bypass from editable `app_users.email` is acceptable.
3. Choose whether user-approved software keys and platform vaults are acceptable if hardware/desktop keyring is missing; do not silently downgrade. A non-exportable key or client assertion of TPM/Secure Enclave is not verified hardware attestation. Mandatory hardware or remote attestation requires explicit approval, verifier/trust-chain policy, availability/support review and an accessibility/recovery plan.
4. Build real authorization integrating existing session validation and strict password reauthentication. `checkConfirmPassword` allows omitted passwords and cannot be used unchanged. Bind session validity and reauth expiration transactionally to enrollment confirmation to close revoke races. Account identity/roles, owner secret changes, administrative actions, mailbox changes and recovery must transactionally revoke dependent factors and native session families. The current mailbox core's account triggers are not session revocation and do not cover owner or external credential rotation. Define an explicit migration/rollback and existing-user data handling plan before activating.
5. Implement versioned production discovery, exact wire schemas, explicit policy/transport readiness gates, production transactions, nonce issuance and cleanup/capacity limits, challenge and enrollment/recovery admission, proof-bound password/OTP issuance, account-independent failure envelopes, timing assessment, request cancellation and all business-route proof enforcement. D1 primary selection/cutover and transactional behavior must be verified on real infrastructure. Fixed-window per-account counters enable targeted lockout; NAT users share IP limits, and same-IP relay remains possible. Evaluate compensating protections and recovery rather than claiming the current budgets solve these risks. Provider delivery and timing remain observable even with uniform errors.
6. Independently review code and threat model, then run real OS/provider/D1 tests, staged load/abuse tests, and audit every network/proxy/Worker/provider log and exception for secrets. Add secret-free aggregated monitoring of challenge/verification, throttling, delivery failures, refresh replay and revocations without labels identifying user/IP. Rehearse operator emergency disable, session/factor revocation and rollback. Rollback must deny existing native credentials even if a previous deployment does not understand them. No deployment, release or production activation is authorized by this PR.

## Required Rust work by platform (not implemented in this repository)

**All platforms:** implement the existing v2 staging discovery and exact schemas in its client contract; do not assume a v3 endpoint exists. Keep username, password and OTP in native accessible controls and zeroize secrets where practical. Use a small temporary visible challenge-only WebView with an isolated ephemeral profile, exact main-frame HTTPS origin/path/port allowlist and separately restricted provider child frames. No login page, JS bridge, DOM, cookies, WebView script/storage/network inspection or token extraction. Block external navigation, popups, downloads, untrusted certificate exceptions and unauthorized permissions. The hosted page posts the Turnstile token directly to the server; Rust polls with transaction proof and uses server results, not WebView events. Cancel/close on expiry, network errors, user cancellation or policy violations; show accessible keyboard and screen-reader controls. Offer an explicit system-browser choice that creates a **fresh** request and code comparison; never silently switch. No Turnstile bypass. The provider's required child-frame/script/network origins and runtime behavior need platform validation; do not expand privileges to hide failures.

Use exact scheme/host/effective-port scope. TLS validation must remain enabled; no secrets, verifier, tokens or credentials in URLs, callbacks, logs, diagnostics or crash dumps. Persist access and refresh tokens together as one encrypted, versioned atomic record in OS-protected storage, protected by an interprocess lock. One refresh in flight across processes; on uncertain/lost refresh response never retry the old refresh, best-effort logout and clear/re-authenticate. Lost OTP response can leave an orphan family; lost logout response does not prove server revocation. Backend absolute expiry and revocation are authoritative. Clock skew must not extend server validity. For future v3, generate a per-origin P-256 key, construct a new nonce-bound ES256 proof per request, convert signatures to JOSE `r || s`, bind `ath` and transaction claims as specified, reject redirects and handle nonce/clock failures without unsafe replay. These are requirements for a future implementation, not currently available capabilities.

**Windows 10/11:** provide supported WebView2 runtime and OS servicing/installation checks; use fresh per-attempt user-data directories and tear them down after WebView process exit. Implement navigation/frame policy with WebView2 APIs and validate that the provider actually works. Use CNG Platform Crypto Provider when available, or explicitly approved CNG Software Key Storage Provider; enforce non-exportable key policy where supported and current-user ACLs. Use DPAPI or Credential Manager for the encrypted token record; CNG stores the key reference separately. Handle TPM provisioning, device/profile reset and roaming as recoverable failures rather than claiming attestation.

**macOS:** use a supported WKWebView / WebKit runtime with a nonpersistent `WKWebsiteDataStore`, strict navigation and child-frame policy; verify cleanup and provider behavior on supported macOS releases. Use `SecKey` P-256 signing keys in Keychain, optionally `kSecAttrTokenIDSecureEnclave` when supported and explicitly selected; Secure Enclave availability/interaction/access-control and algorithm support must be detected. Otherwise offer the user an explicitly approved software Keychain key, not an invisible downgrade. Store the atomic token record in a correctly scoped Keychain item and handle locked keychain, access group, user presence and migration.

**Linux:** choose and document a supported distribution/runtime matrix (e.g. tested WebKitGTK and GTK versions, sandbox/container dependencies and display server); no blanket claim of support until tested. Use an ephemeral WebKitGTK context/profile and enforce equivalent navigation/permission controls; test provider compatibility and accessibility on Wayland/X11. For tokens and an explicitly approved software key, use a properly scoped unlocked Secret Service/keyring with permissions and process locking. Where supported and selected, use a system TPM/PKCS#11-backed non-exportable P-256 key through a reviewed provider. Many headless/minimal systems have neither keyring nor hardware: show a clear unsupported/configuration error or obtain an explicit decision for a separately designed passphrase-protected fallback. Never store a plaintext private key or tokens, silently downgrade, or claim hardware verification from the provider name.

Real Windows, macOS, Linux, WebView/Turnstile, mail provider, D1, cross-platform Rust signatures, attestation and security-review results are **not available**. Automated tests in this PR use Node/WebCrypto and simulated SQLite/D1; they do not establish production compatibility.
