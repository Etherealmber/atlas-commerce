# Prompt: Android Atlas Agent history and Supabase cutover

Work in `Etherealmber/atlas-commerce-android` on the branch assigned to your session. First inspect the current source, tests, release compatibility and the corresponding backend PR/API contract; do not assume the backend cutover or attachment endpoints have been deployed. Coordinate any incompatible changes with the Atlas Commerce Worker. Do not ask for or expose secrets, and do not embed Supabase credentials in the app.

## Goal

Support Atlas Agent conversations backed by the existing Atlas Worker, whose future server-side store will be separate tables in the journal Supabase project. Start the new store empty: do not import legacy R2 conversations or silently republish old local conversations. Server-side conversation history expires after 30 days without a user interaction. User-sent images will be encrypted in private R2 and removed with the conversation, using server-managed authenticated APIs. The Android app must not connect directly to Supabase or R2.

## Current implementation to inspect

At Android main commit `7c10e1eab68b40f5003f612a6ad6e211c9b60386`, `AtlasApi.kt` uses `GET api/admin/agent/threads`, `GET/PUT/DELETE api/admin/agent/threads/{id}`, and `POST api/assist/chat` and `api/assist/chat/stream`. `AgentThreadDetailDto` does not expose response `meta.version`; `PutAgentThreadRequest` has title and messages but no `expected_version`. `AgentViewModel.persistAgentThread` writes snapshots and retries. Message DTOs contain role/text/duration, not saved image bytes; images are sent separately to chat. Verify all of these against the current code before editing.

## Requirements

1. Keep existing API routes, authentication, chat/stream behavior, localization, approval safeguards, real tool results, existing account isolation, and supported Android versions. Never grant actions or modify business data just because the user answers an Agent clarification.
2. Agree and document the exact versioned Worker API first, including response envelopes, opaque version tokens, create-only semantics, stale conflicts, expiry/deletion outcomes, idempotency and attachments. Do not invent endpoint shapes or claim that the backend is ready. Treat the existing draft RPC as incomplete, not a public contract.
3. Parse a thread's version from response metadata; include the correct expected version on writes, including explicit null for create where the agreed API requires it. Serialize writes per conversation and handle delayed responses, multiple devices and account switches. A stale write must not overwrite newer data, and a deleted/expired thread must not be silently recreated. Preserve unsaved edits on conflict and offer safe recovery (for example, save as a new conversation). Never automatically retry a mutation unless the backend provides a tested idempotency contract.
4. Add a clear delete control for saved conversations with confirmation. Delete through the authenticated Worker, not Supabase/R2 directly. Update the UI/cache only after a truthful server acknowledgement; show an actionable error on failure. Account for in-flight saves, replies and uploads, cancellation and other devices. Do not claim images were deleted until the backend confirms its defined deletion contract.
5. Make history loading responsive while preserving accurate loading, empty and error states. Keep title summaries useful, do not issue an unbounded request per conversation, and avoid unnecessary repeat API calls. Follow the backend's pagination and timeout contract; do not promise fixed latency. Show the 30-day inactivity policy in the interface. List/open reads must not extend expiry unless the backend contract explicitly says so.
6. Implement attachment sending and restoration only after the Worker provides the agreed authenticated protocol. Never use public R2 URLs or log image content, credentials or user messages. Respect upload and media size limits, support failed upload/retry, and show truthful unavailable/deleted states. Verify restored images, thread deletion and expiration on a real device and across accounts. Encryption and cleanup are the server's responsibilities, not a client-only encryption substitute.
7. Avoid re-uploading pre-cutover cached chats into the new empty namespace. Version local caches per account/environment, apply a safe migration/reset strategy, and clearly handle local-only unsaved messages; do not silently delete user data. Check logout/account-switch cleanup and 30-day expiration of local copies. Do not import old R2 histories.
8. Keep old Android releases operational during a staged rollout, or explicitly document a minimum-version gate and coordinate it before backend activation. A backend that simply mandates `expected_version` will break older Android clients. Do not weaken concurrency or deletion protection to pretend old versions are safe; design and test a deliberate compatibility policy with the Worker team.
9. Add regression tests for success/failure deletion, stale saves, simultaneous updates, retry after lost acknowledgement, in-flight delete, cache/account isolation, 30-day expiry, user-visible errors and attachment behavior. Test both buffered and streamed responses and approval workflows. Run Android unit/instrumentation tests, build a real APK, test against a non-production Worker and Supabase project, and test at least one supported older APK. Report results and remaining limitations precisely.

Do not deploy, merge, delete legacy objects, change the existing journal configuration, or claim production verification without explicit authorization and demonstrated staging results. Open a PR with the compatibility/rollout plan, exact backend dependencies and tests. If a backend capability is missing, make the app fail safely and explain the blocker rather than inventing or bypassing it.
