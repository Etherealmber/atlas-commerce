# Native desktop password + OTP pilot: 0.9.1 client contract

**Experimental; disabled by default; isolated staging only.** This repository supplies the Worker and the hosted challenge document, not the Rust client or a validated WebView2 runtime. No production readiness, device attestation or passkey support is claimed. Do not enable on production or the existing preview, which shares production resources. See [security, setup and residual risks](desktop-native-auth-v2.md) and the [production-readiness blockers and decisions](desktop-native-production-readiness.md).

## Gates and discovery

Use an isolated Worker, D1, test account, test mail and provider keys. The Worker requires `ENVIRONMENT=staging`, `DESKTOP_NATIVE_V2_PILOT_CHALLENGE=true`, `DESKTOP_NATIVE_V2_PILOT_LOGIN=true`, canonical HTTPS `DESKTOP_NATIVE_V2_PILOT_ORIGIN` including non-default port, a single lowercase non-owner `DESKTOP_NATIVE_V2_PILOT_USERNAME`, test `DESKTOP_NATIVE_V2_PILOT_OTP_FROM` and `_TO`, dedicated secret `_OTP_KEY` (at least 32 characters), `EMAIL`, D1 `prepare`/`batch`, `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`. Account must be active with supported PBKDF2 hash. These checks do not probe actual account, infrastructure, delivery, provider or runtime health.

`GET /api/auth/desktop/v2/capabilities`, with HTTPS, no query, and no cross-origin `Origin`, returns `{success:true,data:{version:2,discovery_enabled,methods,...}}`. For a fully configured exact origin `methods.password_otp` is:

```json
{"available":true,"version":2,"experimental":true,"staging_only":true,"challenge":"system_browser_turnstile","otp_required":true,"challenge_presentation":{"hosted_path":"/login/desktop-challenge","embedded_path":"/login/desktop-challenge-embedded","modes":["embedded_webview","system_browser"],"webview2":"staging_supported_requires_client_validation","system_browser":"explicit_choice_only","same_ip_required":true,"server_verified":true}}
```

The historical `challenge` value remains for compatibility; use `modes` and `embedded_path` for the new mode, not that value alone. When not configured or at a different origin, the method is unavailable. An advertised mode is not proof the client runtime or real challenge works. The separate v1 browser fallback and non-pilot `/v2/password` and `/v2/otp` do not accept this protocol.

## Transport, secrets and request creation

Use HTTPS with certificate validation; compare canonical scheme, host **and effective port**, reject userinfo, paths, queries, fragments and redirects in configured origin. All operations below are relative to `/api/auth/desktop/v2/pilot`, POST JSON, no query; unknown fields are rejected, maximum body 8192 bytes, entire body read timeout 10 seconds. Browser endpoints require same-origin `Origin`; any supplied origin must match the request URL, and `Sec-Fetch-Site` if supplied must be `same-origin` or `none`. No bearer, fingerprint or desktop header gives an exemption. Responses are `no-store` and `no-referrer`. Do not record credential fields, state, verifier, OTP, session/provider tokens, URLs, bodies, headers or provider exceptions in client, crash, proxy, edge, WAF, APM or server logs.

The user enters username and password in native fields first; retain them only in protected native memory until the challenge is verified. Generate distinct random `state` (43–128 base64url characters) and RFC 7636 `code_verifier` (43–128 unreserved characters) with a CSPRNG. `code_challenge` = unpadded base64url SHA-256 of the ASCII verifier. Zero/drop sensitive buffers as far as the runtime permits.

1. `POST /requests`:
   `{"origin":"https://test.example:8443","state":"…","code_challenge":"…","code_challenge_method":"S256","device_label":"Test desktop","presentation":"embedded_webview"}`. Label is 1–60 characters without controls, bidi controls or angle brackets. `presentation` may be `embedded_webview` or `system_browser`; omitted means legacy `system_browser`. The choice is stored server-side per transaction and cannot be changed by the page. Embedded mode requires all login gates and the exact configured origin. Success 201: `{"success":true,"data":{"version":2,"request_id":"<64 lowercase hex>","origin":"https://test.example:8443","pairing_code":"<5>-<5>","expires_in":300,"interval":5}}`. Check all fields before use. No verifier is stored server-side.
2. Construct `origin + /login/desktop-challenge-embedded#request_id=<id>` from validated pieces. Only the random request reference may appear in the fragment; never put a password, OTP, state, verifier, session or provider token in a URL, callback, WebView or logs. The standalone page strips the fragment from history, calls `/browser/prepare`, renders an **always-visible** widget when interaction is required and submits the provider result itself to `/browser/decision`; Rust receives none of it. The page has no password, OTP, login session, app bootstrap, desktop bridge or automatic fallback. A failure message asks the user to return to Atlas.
3. Desktop polls `POST /poll` using proof `{origin,request_id,state,code_verifier}` as four top-level fields. Success 200 `{success:true,data:{status,request_id,origin,interval:5}}`; check returned origin and ID. `status`: `pending`, `verifying`, `verified`, `failed`, `denied`, `cancelled`, `consumed`. Only proof-bound `verified` authorizes continuing. Use a monotonic local deadline, one request at a time, at least 5 seconds between polls, no more than 60 polls, absolute expiry 300 seconds. Honor `Retry-After`; timeout, terminal/unexpected status, user close, navigation/TLS failure or IP change means stop and cancel, not bypass. `POST /cancel` with proof changes `pending`/`verifying`/`verified` to `cancelled`; success `{status:"cancelled"}`. Cancellation cannot undo an already consumed request.
4. Close and destroy the WebView on `verified`. Send native `POST /login/password` with proof plus `{username,password}`; username is trimmed/lowercased and must match `[a-z0-9._-]{1,64}`, password length 1–512. This atomically consumes the challenge. Do **not** call `/consume` for login. Syntax-accepted valid and invalid credentials both return `{success:true,data:{status:"otp_pending"}}`; this does not prove password validity or mail delivery. Mail is sent asynchronously only to the configured test mailbox. Do not replay an uncertain/lost response.
5. Prompt in a native Rust field. `POST /login/otp` with proof and `{otp:"<six ASCII digits>"}`. Maximum five attempts, including attempts before delivery; deadline remains the original request expiry. A single success returns `{success:true,data:{token_type:"Bearer",access_token,refresh_token,access_expires_at,session_expires_at,origin,username,role}}`; timestamps are UTC ISO strings. On wrong, undelivered, expired, replayed or racing OTP, fail generically. After password, use `POST /login/cancel` with proof to cancel `checking`/`pending`; after session use logout. If password or OTP response is lost, do not replay; clear native secrets and restart. An orphaned session may require operator revocation.
6. Store session tokens in the native OS vault partitioned by exact origin. `POST /session/refresh` with `{origin,refresh_token}` returns the same session shape with **both tokens rotated**. Access expires after at most 15 minutes; absolute session lifetime is 12 hours, non-sliding. One refresh in flight; atomically persist the pair. Never retry an uncertain refresh: reuse of a recorded consumed refresh token revokes the family and racing refreshes can revoke the winner. The server records only hashes of refresh generations consumed after this upgrade and preserves the last pre-upgrade generation on first rotation; still older pre-upgrade generations cannot be recovered or detected. `POST /session/logout` with `{origin,refresh_token}` returns `{status:"revoked"}` for the current or a recorded previously consumed refresh. On uncertain refresh, logout with the last locally held refresh is a best-effort way to revoke the family, not to recover tokens. Clear locally even if logout fails; server revocation is not guaranteed on a lost response. These are bearer sessions, not cryptographically device-bound.

## Hosted endpoint schemas and mode selection

The page calls `POST /browser/prepare` with `{origin,request_id}`. Response data: `{request_id,origin,device_label,pairing_code,presentation,site_key,action,cdata,expires_at}`; `action` is `atlas_desktop_v2`, `cdata` is 64 random lowercase hex, expiry ISO UTC. The embedded page requires `presentation:"embedded_webview"` and validates identity, action, cdata and the expiry timestamp format. It does not trust the local wall clock for expiration: the server checks its own expiry on every operation, while the page also limits its display to five minutes after preparation. Rust must enforce the creation deadline with a monotonic timer. It posts `/browser/decision` `{origin,request_id,decision:"approve",turnstile_token}` itself. The system-browser mode instead uses `/login/desktop-challenge#request_id=<id>`, displays the origin and pairing code, and posts approval with `compare_confirmed:true` after explicit comparison; `decision:"deny"` is also supported. Old requests with no stored presentation retain system-browser comparison. Siteverify is called by the server, which validates success, hostname, exact action and transaction cdata; it claims `pending→verifying` before the call and sets `verified` or `failed`. A provider timeout is five seconds. Cancellation or expiry while verification runs wins. A crash may leave `verifying` until expiry. The standalone `/consume` only consumes a verified challenge and issues **no** session.

If WebView2 is missing or fails, show an explicit native choice. If the user chooses system browser, cancel the original request and create a fresh request with `presentation:"system_browser"`, preserving comparison and polling; never switch automatically. A browser or CAPTCHA is not an attestation of the client or user.

Errors use `{success:false,code,error}`: 400 `INVALID_REQUEST`/`HTTPS_REQUIRED`, 408 `REQUEST_TIMEOUT`, 401 `INVALID_PROOF`/`AUTH_FAILED`, 403 `ORIGIN_MISMATCH`/`CHALLENGE_FAILED`, 409 `NOT_APPROVED`/`USED`, 410 `EXPIRED`, 429 `RATE_LIMITED`/`SLOW_DOWN`, 503 `METHOD_DISABLED`/`UNAVAILABLE`; global guards can also return 413 or 403. `Retry-After` may be present. Budgets: five creations/IP/five-minute fixed window per desktop protocol, plus eight creations/IP/five minutes shared across desktop v1, v2 phone and v2 pilot when the staging challenge flag is enabled; 90 other operations/IP/minute, separate password and OTP limits of 20/account and five/account+IP per ten minutes, and eight refresh attempts per session family per ten-minute fixed window. After challenge verification, pilot password/OTP also share the existing website credential budgets: 60/IP/minute, 300/IP/ten minutes, 20/account/ten minutes (shared between password and OTP), and five/account+IP+purpose/ten minutes. This intentionally couples channels at the abuse threshold and can throttle legitimate website attempts after native abuse (and vice versa); an unverified challenge does not consume those shared slots. Attempts reserve budget even if a later operation fails; denied refresh does not rotate. Logout is not subject to the refresh-family budget. Shared IPs/fixed windows can cause false failures. Desktop, browser decision and proof-bound calls must have the same observed IP; VPN or address changes can fail. A same-IP NAT or relay can still be abused.

## Required WebView2 integration (not implemented here)

Use a small **visible** temporary WebView with a fresh, isolated per-attempt profile; allow its own storage/cookies as needed for the challenge, but Rust must never read, copy or export them. Delete the profile after its process exits. Do not inject JS, evaluate scripts, inspect DOM, local storage, cookies, network request/response bodies, provider token or WebView messages; do not add host objects, JS bridges, DevTools or network recording. Restrict permissions and disable popups, external navigation and downloads. Handle certificate errors by cancellation, not exceptions.

Install navigation handlers before first navigation. Permit main-frame navigation only to the exact HTTPS origin including effective port and fixed embedded path, with at most the single initial `request_id` fragment and no query; also permit that same path with no fragment after history replacement. Reject all other schemes, origins, paths, redirects and top-frame navigation, including top-frame attempts from a child frame. Do not infer success from navigation, title, URL, WebView close, a message or callback. Allow the provider's child frame origin `https://challenges.cloudflare.com` and transient internal `about:blank` as necessary; keep child-frame handling distinct from top-frame policy. The page loads same-origin script plus provider script, connects to same-origin browser endpoints and provider, and embeds the provider frame. Its CSP is `default-src 'none'; script-src 'self' https://challenges.cloudflare.com; style-src 'unsafe-inline'; connect-src 'self' https://challenges.cloudflare.com; frame-src https://challenges.cloudflare.com; img-src 'self' data:; base-uri 'none'; form-action 'none'; object-src 'none'; frame-ancestors 'none'`. These restrictions do not make a compromised same-origin server safe, nor substitute for navigation handlers. Do not widen them blindly if provider dependencies change; test and document in isolated staging. Fresh profiles are important to avoid pre-existing service workers. Keep the window keyboard-accessible and visible, provide an accessible native cancel control and preserve a readable status for assistive technology; do not infer CAPTCHA success from accessibility events. Real keyboard, screen-reader and provider interaction, WebView2/OS behavior, network policy, test mail, D1 and effective logs remain unverified here.
