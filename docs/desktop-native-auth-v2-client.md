# Desktop native password + OTP pilot: client contract

**Experimental, disabled by default, staging only. Not production-ready.** This describes the backend in this repository, not a Rust implementation or a verified WebView2 integration. Use an isolated staging Worker, HTTPS origin, D1, Turnstile keys and test mailbox; the existing preview shares production resources and is not staging. See [the detailed security and deployment notes](desktop-native-auth-v2.md). Do not enable production without independent review and an explicit risk decision.

## Discovery and transport

`GET /api/auth/desktop/v2/capabilities` returns `data.methods.password_otp`. When configured for the exact requested origin its object is:

```json
{"available":true,"version":2,"experimental":true,"staging_only":true,"challenge":"system_browser_turnstile","otp_required":true,"challenge_presentation":{"hosted_path":"/login/desktop-challenge","webview2":"unverified_requires_client_validation","system_browser":"explicit_choice_only","same_ip_required":true,"server_verified":true}}
```

The historical `challenge` value is retained for compatibility. The new presentation metadata is a contract proposal, **not evidence** that WebView2 works. Discovery checks configuration, not real D1, mail, provider, client or log health. The login requires `ENVIRONMENT=staging`, flags `DESKTOP_NATIVE_V2_PILOT_CHALLENGE=true` and `DESKTOP_NATIVE_V2_PILOT_LOGIN=true`, the exact HTTPS `DESKTOP_NATIVE_V2_PILOT_ORIGIN` including port, one configured lowercase non-owner test username, fixed test sender and mailbox, a dedicated OTP MAC secret of at least 32 characters, EMAIL and D1 bindings, and Turnstile keys. The account must be active and use the supported PBKDF2 password format. Never send credentials to the unavailable non-pilot `/v2/password` and `/v2/otp` endpoints.

All paths below are relative to `/api/auth/desktop/v2/pilot`. POST JSON, no query, validate the HTTPS certificate, do not follow redirects, and compare the canonical origin including effective port. Browser requests require `Origin` equal to that origin. Bodies are at most 8192 bytes, read within 10 seconds, and reject unknown fields. Responses use `no-store` and `no-referrer`. Do not log credentials, proofs, URLs, tokens, headers, responses or provider exceptions. There is no desktop header or fingerprint authentication exemption.

Generate distinct CSPRNG values in native memory: `state` is 43–128 base64url characters, `code_verifier` is 43–128 RFC 7636 unreserved characters, and `code_challenge` is the 43-character unpadded base64url SHA-256 of the ASCII verifier. `request_id` is 64 lowercase hex characters. A `proof` below means the four **top-level** fields `{origin,request_id,state,code_verifier}`, not a nested field.

## Operations and state

All successful responses have `{success:true,data:{...}}`; errors are `{success:false,code,error}`.

1. `POST /requests` with `{origin,state,code_challenge,code_challenge_method:"S256",device_label}`; label is 1–60 characters, without controls, bidi controls or angle brackets. Returns 201 `{version:2,request_id,origin,pairing_code,expires_in:300,interval:5}`. Display the origin and pairing code in Rust. Construct `origin + /login/desktop-challenge#request_id=<id>`; the reference is the only fragment value. No password, OTP, state, verifier or token goes in a URL.
2. Open the hosted page in a temporary WebView2 **only after** implementing and validating the controls in the detailed document. It shows the challenge, origin and code; compare the code and confirm. Rust owns all credential fields. The page posts `/browser/prepare` and `/browser/decision` itself and sends the Turnstile token directly to the server; Siteverify validates hostname, action `atlas_desktop_v2`, and server-generated transaction `cdata`, failing closed. Rust must not inject scripts, intercept requests, inspect DOM/cookies/storage, or receive a token through a bridge. The only Turnstile frame origin currently expected is `https://challenges.cloudflare.com` (with transient `about:blank`); the deployed CSP is shared and broader, and real dependencies must be verified in isolation. Only allow the exact HTTPS origin **and port** and fixed challenge path for main-frame navigation, including redirects; reject popups, downloads, permission requests and TLS errors. Test actual WebView2 behavior. The user may explicitly select the system browser instead; never switch automatically.
3. `POST /poll` with proof returns 200 `{status,request_id,origin,interval:5}`. Status can be `pending`, `verifying`, `verified`, `failed`, `denied`, `cancelled`, or `consumed`. One poll in flight; at least 5 seconds apart, at most 60 polls, within 300 seconds. Respect `Retry-After`. Only a proof-bound poll showing `verified` permits password submission. Failure, denial, timeout, expiry, cancellation, navigation violation or IP change means stop, cancel where possible, clear secrets, and begin a new transaction. `POST /cancel` with proof changes pending/verifying/verified to cancelled and returns `{status:"cancelled"}`; a completed/expired/terminal transaction cannot be recovered.
4. `POST /login/password` with proof plus `{username,password}`. Username is trimmed/lowercased and must match `[a-z0-9._-]{1,64}`; password is 1–512 characters. The verified challenge is consumed atomically **by this call**. Do not call `/consume` for login. On accepted syntax the generic response for valid and invalid credentials is `{status:"otp_pending"}`; it does not prove the password or mail delivery succeeded. OTP is sent asynchronously only to the configured test mailbox for the allowed account. A lost response is not recoverable; do not replay, cancel if possible and restart.
5. `POST /login/otp` with proof plus `{otp:"<six ASCII digits>"}`. At most five attempts per transaction; attempts before delivery also count. OTP expiry is bounded by the original 300-second transaction. Wrong, undelivered, expired, replayed or raced OTPs fail generically. A single success returns `{token_type:"Bearer",access_token,refresh_token,access_expires_at,session_expires_at,origin,username,role}` (UTC ISO timestamps). Store tokens in the native OS vault partitioned by exact origin. Access expires in at most 15 minutes; the absolute session lifetime is 12 hours, non-sliding. A lost OTP response cannot be recovered; restart. An orphan session can persist until expiry or operator revocation.
6. After password use `POST /login/cancel` with proof, returning `{status:"cancelled"}`; after a session use logout. Cancellation and account changes invalidate pending work. A request already authorized before revocation may finish.
7. `POST /session/refresh` with `{origin,refresh_token}` returns the same session shape with **both tokens rotated**. The refresh token is 64 lowercase hex characters. Allow exactly one refresh request in flight per session and atomically persist the returned pair. **Never automatically retry a refresh with an uncertain/lost response**: reuse of the immediately previous refresh token revokes the family, and competing refreshes can revoke the winner. On uncertain result or refresh failure, clear local credentials and require a fresh login; an operator can revoke an orphan server session. Older refreshes are not all tracked.
8. `POST /session/logout` with `{origin,refresh_token}` using the current refresh returns `{status:"revoked"}`. Clear local tokens even if logout fails or its response is lost; server revocation is not guaranteed in that case. The operator can revoke it in D1. Disabling flags suspends access but is not permanent revocation.

Errors can include 400 `INVALID_REQUEST`/`HTTPS_REQUIRED`, 408 `REQUEST_TIMEOUT`, 401 `INVALID_PROOF`/`AUTH_FAILED`, 403 `ORIGIN_MISMATCH`/`CHALLENGE_FAILED`, 409 `NOT_APPROVED`/`USED`, 410 `EXPIRED`, 429 `RATE_LIMITED`/`SLOW_DOWN`, 503 `METHOD_DISABLED`/`UNAVAILABLE`; global guards may return other errors, including 413 and 403. Treat all as failures, not permission to bypass. Budgets include five creations/IP/5 min, 90 other operations/IP/min, and separate password/OTP limits of 20/account and 5/account+IP per 10 minutes. OTP is limited to five attempts; fixed windows and shared IPs can produce false failures or quota exhaustion.

The creating desktop, browser decision and proof-bound requests must have the same observed IP. VPNs, multi-network routing, IPv6 changes and proxies can cause false failures. Same-IP, fingerprint, desktop headers and CAPTCHA do **not** establish client integrity or that the same person solved the challenge; shared NAT and CAPTCHA relay remain possible. Generic failures do not guarantee uniform timing, and targeted account/IP quotas can be exhausted. Real Windows WebView2, Cloudflare/D1, test-mail and effective Worker/proxy/WAF/export log-redaction validation are still mandatory and have not been performed here. Use only synthetic, non-secret markers for log checks.
