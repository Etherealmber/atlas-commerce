# D1 usage and encrypted journal rollout

## Evidence

The manually dispatched, read-only [D1 insights run](https://github.com/Etherealmber/atlas-commerce/actions/runs/45852549178) returned aggregated query data for `company-stock-db` over a rolling one-day window. `INSERT api_log` ran 22,241 times, with 88,964 rows written and 889,640 rows read reported for that query shape; QR session-status SELECT ran 19,089 times, and QR session creation INSERT ran 1,343 times (4,029 rows written). These are query analytics for that window, not the account-wide UTC-day billing counter, and they do not establish which requests produced the journal entries. No production rows or schema were modified by that workflow. The prior workflow sorted by reads/count only and incorrectly reported success even when every Cloudflare query failed; it now explicitly includes writes, exits on errors, and outputs only aggregate operation/table labels and metrics instead of raw SQL.

The API journal records requests asynchronously with two secondary indexes and an AUTOINCREMENT primary key. Repeated successful, unclaimed pending QR status checks are now excluded from the D1 API journal; error responses, claimed/approved/denied/expired states and all QR mutation requests remain eligible. Other existing exclusions include probes and demo traffic. The journal UI states this limitation; journal statistics are not total request counts. Login QR polls run at four-second intervals and pause in hidden tabs; expired sessions still require a fresh QR. Changes apply after deployment, not retroactively. Don't weaken auth, revocation checks or business/security `audit_log` to cut usage.

## Encrypted archive: staged, not a D1 cutover

An optional **shadow** archive writes independent AES-256-GCM `.journal` objects to a separate private R2 bucket, using random IVs and authenticating the object name. The existing D1 journal and audit UI remain authoritative. Eligible idle QR polls are mirrored to R2 in shadow mode even though they are omitted from D1; existing probe/demo exclusions still apply. Values are restricted to the existing API journal fields; query strings, authorization headers, cookies, request/response bodies, and QR tokens are not intentionally stored. Never attempt to collect arbitrary headers or bodies: they can contain credentials or customer data. Encryption does not protect data if the key or an authorized endpoint is compromised.

This is **disabled by default** and has not been enabled in production. The dedicated bucket and lifecycle rule were created by workflow run 45856677472; verify public access and retention independently before binding it. To stage it, an operator must:

1. Provision a dedicated R2 bucket with no public domain or public access. Do not use the existing public-facing `IMAGES` bucket. Bind it as `JOURNAL_ARCHIVE`; ensure CI preview bindings remain isolated.
2. Configure an R2 lifecycle expiration rule for `api-journal/v1/` after 30 days, and verify actual cleanup. R2 lifecycle is mandatory: the application limits reads to 30 days, but does **not** automatically delete objects. This is not a precise deletion SLA; lifecycle execution may be asynchronous.
3. Securely generate a unique random 32-byte key, store its base64 representation as the Cloudflare Worker secret `JOURNAL_ENCRYPTION_KEY`, and set `JOURNAL_ARCHIVE_MODE=shadow`. Never put the key in Git, workflow logs, chat or the public bucket. The `AJR1` format currently supports **one active key**: changing or losing it makes old objects unreadable. Implement key versioning and a recovery/rotation procedure before rotation or cutover.
4. Test on an isolated environment, verify authenticated owner/admin-only `GET /api/admin/journal-archive?day=YYYY-MM-DD` and `/api/admin/journal-archive/item?key=...`, paginate the listing, verify encryption, denial of unauthorized access, retention, and independently monitor `journal_archive_write_failed`. A missing or invalid key or an R2 error cannot break a request; D1 remains unchanged. Shadow writes use `waitUntil` and can fail, so this is not a guaranteed complete archive.
5. Estimate R2 costs: this first version writes **one object per eligible request**, so it may consume significant Class A operations and listing/decryption is not a substitute for indexed queries. Implement durable batching, retry/alerts, key versioning, and a searchable/paginated audit UI with complete stats before production cutover. Also plan access-control review, legacy D1 journal continuity, rollback, and privacy/deletion requirements. No D1 records are migrated or deleted by this feature, and business `audit_log` remains in D1.

The manual production migration workflow has a read-only `list` action; `apply` and `setup-target` modify production and require an explicit confirmation. The local migrations guard uses a throwaway DB. Do not run a production migration just to enable this shadow archive; the archive code itself needs no D1 migration.

### Provisioning attempt and demo AI

The manual D1 workflow also offers `journal-setup`, requiring the exact confirmation `CREATE-JOURNAL`. It only attempts to **create a new** `atlas-commerce-private-api-journal-1` bucket (never adopts an existing bucket), adds an `api-journal/` 30-day lifecycle rule and displays public-access settings. If a step fails after creation, the bucket may exist without the lifecycle rule: inspect it and finish configuration manually; do not blindly rerun or bind it. Confirm both the development URL and custom domains are disabled. This does not install encryption keys, bind the bucket, deploy the Worker, enable shadow mode, remove D1 data, or provide batching/retries.

The public test/test sandbox strips other production credentials deliberately. At the user's request, demo assistant routes may use the same server-side `GROQ_API_KEY` (a separate `DEMO_GROQ_API_KEY`, if supplied, takes precedence). The credential is never returned to the client. A durable global daily budget of 20 chat requests and a per-sandbox budget of 5 are checked before each call, including failures, and fail closed if unavailable. Demo replies are capped at 200 output tokens (160 for product descriptions), tools at one round, and demo input is text-only. These are not hard token or spending caps: prompts, tools, provider retries/fallbacks and concurrent requests still consume tokens. A public demo sharing the production key can consume the production quota and interrupt real users; configure provider-side limits, monitor usage and prefer a separate low-limit key. Demo inputs and fake sandbox data are sent to Groq. This change is not deployed.

### Security and storage inventory

The existing `IMAGES` bucket contains public-facing image assets alongside sensitive encrypted backups and chats. Verify its public URLs and any custom domain; encryption alone is not equivalent to a private bucket. Backups use AES-GCM and key fallbacks (`BACKUP_ENCRYPTION_KEY` / `ADMIN_BACKUP_TOKEN`); changing keys without retaining old keys can make restores impossible. `.conv` transcripts use AES-GCM, but older plaintext transcript objects may still exist, and the older `.agent` thread format previously allowed a hardcoded fallback encryption key and plaintext KV fallback. New `.agent` writes now fail closed without a secret and no longer create plaintext KV copies. This does not re-encrypt or delete legacy objects; assess exposure and migrate them securely with tested backup/restore before changing secrets. On a reply, strictly recognized legacy plaintext `.conv` line transcripts are encrypted in place with an R2 ETag conditional write before use, if an encryption key is configured; unknown formats, invalid ciphertext, oversized legacy objects and missing/changed keys fail closed and remain untouched. Plaintext has no authenticity guarantee: migration cannot establish whether it was altered before encryption. It does not migrate inactive conversations or older JSON/`.agent` formats. Replies use conditional writes to avoid overwriting concurrent changes. Keep recoverable, access-controlled backups and old keys; test recovery before deployment. Object names and metadata may expose identifiers even when contents are encrypted.

D1 holds relational, indexed business records (including invoices, stock, users and security audit), which should not be moved wholesale to object storage. Candidates for R2 include encrypted immutable exports, backup snapshots and large attachments, with private buckets, lifecycle rules and tested recovery. The former `mail_messages` table can contain invoice email bodies; another route still inserts sent invoice email records if Resend is configured. Removing the mailbox UI did not prove the table has no business or legal value. The v5 backup table list does not include `mail_messages`, so ordinary snapshots may not protect these rows. Do not delete until its contents, required retention and a tested independent backup are verified. The manual `mail-inventory` action reads aggregate counts only and makes no changes. Existing cleanup covers expired OTPs/WebAuthn challenges, login attempts older than 14 days, idempotency entries older than 7 days, and journal/audit logs older than 30 days, subject to the existing triggers. Deleting indexed D1 rows itself costs writes and does not immediately solve an exhausted quota.

The `journal-check` action verified on run 45859297998 that the dedicated journal bucket had no enabled public development URL or custom domain and that its prefix rule expires objects after 30 days. This is a point-in-time configuration check, not proof that every historic or other bucket is private.

The read-only [mail inventory run 45859413149](https://github.com/Etherealmber/atlas-commerce/actions/runs/45859413149) counted 129 mail rows, all older than 30 days, 2 older than 90 days, and 128 with non-empty R2 references. This did not inspect message contents or confirm the referenced objects exist. No rows or objects were deleted; a safe export must account for both D1 metadata/bodies and referenced objects.

### R2-first implementation (not yet activated)

An explicit `JOURNAL_ARCHIVE_MODE=r2` sink has been implemented: eligible records first attempt encrypted R2 storage and fall back to D1 on an immediate R2/key error; pending QR polls stay excluded. The audit panel now has a separate, date-based archive browser; its original D1 filters and KPIs do not include the archive. This is not yet a production cutover: it still writes one object per request using `waitUntil`, without a durable queue, batching, retries, complete cross-store search or comprehensive statistics. D1 fallback may consume quota when R2 is unavailable; asynchronous execution is not a delivery guarantee. The bucket binding, securely backed-up key, deployment, monitoring and a tested recovery plan are still required. Do not set the mode in production until those limitations are accepted and verified.

The user confirmed the inventoried old mail was test data and authorized removal. A guarded workflow targets exactly the inventoried D1 rows, excluding newer rows and refusing a changed inventory; it intentionally does not delete referenced R2 objects without establishing their namespace and whether they are shared.

The guarded deletion attempt [45863189211](https://github.com/Etherealmber/atlas-commerce/actions/runs/45863189211) was rejected by Cloudflare with D1 error 7500 (token lacks permission). A read-only inventory after earlier failed attempts still showed 129 rows. No referenced R2 objects were targeted. The GitHub production Cloudflare token needs the appropriate D1 write permission before retrying; never add token values to logs, workflow inputs or chat. Re-inventory immediately before any retry and stop if it differs.

### What the two panels and backups currently cover

The detailed history panel reads the business/security `audit_log` (actions such as login, payroll and Agent use). The API calls panel reads `api_log` (request status/timing); the two answer different questions and a single request may produce entries in both. Neither old business-audit rows nor old API rows have been migrated into the dedicated R2 archive. The API journal has an optional, disabled-by-default R2 sink; business audits remain D1-authoritative, with a new optional, disabled-by-default best-effort shadow described below. The archive browser is separate from D1 metrics and filters. In particular, successful idle unclaimed QR polls, probes and demo traffic have intentional exclusions: "all" cannot mean every request with the current policy.

The application v5 backup is not a complete database or R2-bucket backup. It exports an explicit allowlist of D1 tables, including business `audit_log` and `assist_audit`, but not `api_log` or `mail_messages`; capped log tables retain only the most recent 5,000 rows, and other queries have a 200,000-row cap. Missing/failed tables can be recorded as skipped. It lists at most 5,000 R2 object keys without copying the objects; those objects (including images and chats) can be lost independently. It also does not back up the dedicated journal bucket, Worker secrets, configuration outside the captured tables, or unlisted tables. `ABK1`/`ABK2` encrypt snapshots in the shared `IMAGES` bucket, but restore depends on retained secrets and is best-effort per allowlisted table. Do not claim a complete recovery without a separate database-level backup, object-copy strategy and successful isolated restore drill.

### Requirements before migrating both journals

Do not delete or switch off D1 logs merely because the new bucket exists. A safe rollout needs a separately authorized and resumable backfill for both tables (stable original IDs/timestamps, paginated consistent snapshots, idempotent destination keys, retained 30-day policy, and reconciliation of counts and hashes without exposing content); a durable new-event path with retries, dead-letter monitoring and independent D1 fallback; secure key versioning, private access checks, retention, unified history/search and statistics; and an end-to-end isolated restore/rollback drill. Only after reconciliation and owner review should an operator configure keys/binding and cut over. None of those production actions has been performed here.

A preliminary `worker/lib/journalBackfill.ts` building block now copies bounded, ordered pages from **either** D1 table into encrypted `journal-backfill/v1/` objects without deleting D1. The caller supplies a stable, database-specific namespace, ID cursor and upper watermark. It uses conditional create and reads back, authenticates and compares the complete row after every write or retry, failing on mismatch. This per-row check does not prove the source snapshot is complete or authorize deletion. It has no operator endpoint or scheduled backfill job. A disabled-by-default live audit shadow now calls it after a successful D1 write, but it is not a durable migration or complete replication path. Existing D1 rows are copied verbatim, so review historical API paths and audit details for sensitive content before using it. Object names expose the database namespace, table and ID. R2 conditional-create semantics and concurrent retries must be verified on real R2 before use. A namespace must never be reused across independent databases or divergent restores. JSON comparison is strict, so a changed row or different serialization stops the page; investigate rather than overwrite. A watermark alone is not a consistent snapshot and cannot prevent retention deletion or updates during copying. This separate prefix is not covered by the existing `api-journal/` lifecycle rule or archive browser: define and verify retention and access explicitly before any deployment. Additional reconciliation, scheduling, durable ongoing audit/API replication, recovery, monitoring and production authorization are required. No production migration or live audit replication has been established by adding this helper or shadow path.

The requested policy is 30 days for both journals. Backfilled objects are created later than their event timestamps, so a simple 30-day R2 lifecycle from object creation does not enforce 30 days from the event. A tested expiry mechanism based on event time, lifecycle delays, privacy review and handling of rows already older than 30 days are required before rollout. Existing D1 retention may purge rows independently; no existing purge implies successful R2 copying. Never enable deletion of copied D1 rows until complete reconciliation, independently verified recovery and archive-backed UI/search are in place.

### Worker promise and R2 list incidents

The observability message about a promise belonging to an ended request is consistent with previously shared in-flight schema initialization and creator-column promises. The code now caches completed results rather than those I/O promises; concurrent cold requests can repeat idempotent schema checks, increasing cold-start D1 traffic. Two legacy migration initializers, which can rebuild tables, instead wait briefly using request-owned timers if already running in the same isolate, then fail closed if still busy. An abandoned initializer could leave its in-memory busy marker until that isolate is recycled; this guard is not a distributed migration lock and does not make existing legacy rebuilds safe across isolates or concurrent writes. Review the migration approach separately before running legacy rebuilds. FTS repair no longer shares its in-flight promise either. Verification in a real deployed Worker with canceled and concurrent cold requests remains necessary.

R2 list calls now omit absent cursor options instead of explicitly passing `undefined`, which can be rejected by the Workers binding. This addresses a plausible cause of the cursor TypeError, not proof about every historical occurrence. D1 free-tier read exhaustion, D1 overload, HTTP 500/503, network failures and scan detections are distinct issues; neither fix increases D1 quotas, proves the scans were successful attacks, nor proves all historical errors resolved. Monitor each separately after deployment.

### D1 purge pause pending verification

The branch pauses automatic deletion of both D1 journal tables because archive completeness and recovery are not yet verified. This prioritizes the requested no-delete-before-verification rule: D1 entries can remain **longer than 30 days**, so the 30-day retention objective is not currently met and storage/privacy impact must be reviewed. This code is not deployed merely by merging or pushing. Production continues its existing 30-day purge until a deployment changes it. Do not resume deletion until an independently tested end-to-end archival, reconciliation and retention design is in place. R2 lifecycle alone does not prove D1 rows were copied or recoverable.

The offline helper now also offers `verifyJournalPage` for a separate read-only pass that authenticates each destination object and compares the full source row. It neither modifies nor deletes data and is not wired to production. A page-by-page match is not complete migration proof: it cannot establish a stable whole-source snapshot, detect destination-only extras, guarantee a durable live tail, validate event-time expiry or replace an isolated restore test.

### Missing recent audit events

The audit table view reads D1, not the R2 archive. Previously it could also remain cached while the settings tab stayed open or was reopened; the updated view refreshes the first page periodically only while visible and reports a loading failure instead of presenting it as an empty journal. Timestamps in the list use browser-local time; the stored audit timestamp in details is UTC.

`writeAudit` historically swallowed storage failures to avoid breaking business requests. When D1 rejects an insert (including after quota exhaustion), the event may never be stored; the current API-only R2 archive does not recover it. A newer Worker emits the fixed, content-free `audit_journal_write_failed` signal on a failed audit write, without credentials, identities or raw database errors. This is diagnostic only, not a durable queue, alert, or recovery mechanism, and it cannot diagnose past failures retroactively. Check Cloudflare Worker logs and D1 usage for the affected interval, confirm local versus UTC timestamps and active filters, and compare a fresh D1 query once available. Do not claim the missing events were archived or reconstructed.


### Optional audit shadow — staging only

A new `JOURNAL_AUDIT_SHADOW=1` flag can schedule a read-verified encrypted copy of each successfully inserted D1 audit row through request-owned `waitUntil`, using the `journal-backfill/v1/` format. It defaults off; it is not bound or deployed by this change. It requires a dedicated private `JOURNAL_ARCHIVE`, a secure 32-byte `JOURNAL_ENCRYPTION_KEY`, and an immutable source-specific `JOURNAL_AUDIT_NAMESPACE`; if a second database is configured, an independently unique `JOURNAL_AUDIT_TARGET_NAMESPACE` is also mandatory. Demo and different-database requests are excluded. It writes one object and reads it back per event, adding R2 operations and a D1 read. Events whose D1 insert fails are not copied. Request interruption, R2 failure, lost `waitUntil` work or a disabled/misconfigured flag can leave gaps; fixed diagnostic codes do not provide retries. This is **not a durable queue, archive-backed UI, historical backfill, 30-day retention, or proof of complete recovery**.

Do not enable in production before verifying real R2 conditional-create behavior and concurrent retries, defining lifecycle for this prefix and event-time expiry, reviewing historical and new audit details for sensitive data, monitoring gaps and testing restore and reconciliation. IDs can collide if a namespace is reused for different databases or divergent restores. Never delete D1 data based on a successful shadow write; missing events cannot be reconstructed from it. The fields in the existing device-information display were never captured in this path. Browser private mode, ad-blocker status, graphics hardware and refresh rate cannot be reliably inferred from HTTP requests, and adding new device fingerprinting requires a separate privacy/consent design.

### Storage boundaries and the demo

Business data (such as products and invoices), authentication, Agent controls, knowledge, and audit records use D1 in the ordinary application. Agent conversations can use encrypted R2 objects when the relevant bucket and encryption key are configured; the browser also maintains local conversation state. API and business journals are **not** fully migrated to R2. The Agent may need database access to check the user's permissions and limits and to answer questions using current business records; an LLM provider supplies generated text, not the authoritative stock or invoice data.

A `test` / `test` demo login goes through a gateway before the normal application. It receives an allow-listed environment whose DB binding is a D1-compatible proxy to an isolated Durable Object SQLite sandbox. Production source and target D1 bindings are not supplied. The sandbox has its own temporary business data and security/audit rows, and its scheduled alarm deletes its Durable Object storage after the session. A runtime guard rejects a real D1 binding when constructing the demo environment. Namespaced Durable Objects still maintain rate limits and other session services; demo image/conversation objects, when written, use a separate R2 prefix, whose cleanup must be verified separately. Browser local storage and provider-side processing are also separate from the sandbox database. This does **not** mean there is no storage anywhere or that all R2 data is automatically deleted at session expiry. Unauthenticated traffic that does not carry a demo token is not identifiable as demo traffic.

The documented Cloudflare D1 daily quota error is now mapped to a safe actionable 503 when that specific error reaches the central error handler. A generic Agent error, provider failure, authentication failure or swallowed error is not proof of quota exhaustion; check the correlated Worker logs and Cloudflare metrics. Mapping this message does not reduce usage or prevent exhaustion.
