# Supabase-only journal cutover

This implementation uses a dedicated Supabase project's Postgres as the primary store for new API and audit journal events. It does not write new Supabase-mode events to the journal R2 bucket or to the D1 journal tables. Existing R2 and D1 journal history is not imported or deleted. The Agent and product images still use their separate existing R2 storage. When Supabase mode is active, existing encrypted outbox items are also delivered to Supabase, regardless of their previous R2 destination. Old R2 and D1 records are not imported; their storage remains untouched.

## Security and privacy

The Worker authenticates and authorizes journal viewers using existing owner/admin checks. Only the server sends the Supabase secret to the Data API; it must never be shipped to browsers, mobile apps, logs, source control, or chat. Use a dedicated Supabase project. `public.atlas_journal` has RLS enabled and no anon/authenticated table or RPC privileges; only the server-side service role can execute the narrowly scoped functions. A Supabase secret key is powerful and bypasses RLS: protect it, rotate it on exposure, and do not reuse it outside the journal project. Do not enable automatic public table grants. Verify with Supabase's security advisor.

Journal records are stored as searchable JSON in Postgres, **not encrypted with the journal's application key at rest**. They can include usernames, IPs, user agents, and audit details. Supabase hosts the data in its selected region. Data sent to Supabase, their platform-side encryption, access controls and the project's privacy/compliance obligations are different from the previous application-encrypted R2 archive. The Durable Object outbox retains encrypted records in Cloudflare until acknowledged.

## Provision and test before activation

1. Create the dedicated Supabase project with Data API enabled and public auto-grants disabled. In its SQL editor run `supabase/journal.sql`. It creates the journal table, service-role-only RPCs, indexes, and an hourly `pg_cron` cleanup job. If any SQL or scheduler step fails, **do not switch production**. Verify that `atlas-journal-retention` exists and runs successfully in the Supabase Cron dashboard. Reads exclude rows older than 30 days; the hourly cleanup can leave expired physical rows for up to an hour or longer if the job fails. Failed jobs must be monitored.
2. In Cloudflare Worker settings set **server-side secrets** `SUPABASE_JOURNAL_URL` (the `https://<project-ref>.supabase.co` Project URL) and `SUPABASE_JOURNAL_SECRET_KEY` (a server-only Supabase `sb_secret_...` key, or legacy `service_role` JWT). Do not use the publishable/anon key. Retain the current 32-byte base64 `JOURNAL_ENCRYPTION_KEY` and the `JOURNAL_BUFFER` binding: both are needed for the encrypted outbox and retries. Never change the key while entries are pending. No secrets should be pasted into chat or committed.
3. Deploy and verify the new code in an isolated non-production environment first, with `JOURNAL_ARCHIVE_MODE=supabase`, a dedicated test project, secret and buffer. Test audit and eligible API capture, queue drain, owner-only pages, period filters and charts, outages and retries, duplicate acknowledgment, RLS/anon denial, 30-day cleanup, and actual Supabase limits. Monitor 503s and the buffer health endpoint. The repository tests use mocked HTTP and local Postgres; they do **not** verify your live project, secrets, pg_cron, connectivity or deployment.
4. The repository now sets `JOURNAL_ARCHIVE_MODE=supabase` for production. Do not deploy until the schema, credentials, outbox encryption key, queue health and connectivity have been verified. Pending encrypted outbox items are redirected to Supabase when this mode is active, so no journal R2 writes occur after cutover. Confirm both journal types with real events, queue drain, chart counts and the cron job. Do not remove historical data or storage automatically. If an earlier R2 write succeeded but its acknowledgement was lost, its queued event will also appear in Supabase; old R2 history is not imported or reconciled.

There is no journal fallback to D1 or R2 when Supabase mode is active. Missing configuration may prevent capture; during service outages events already accepted by the encrypted Durable Object remain queued, subject to its capacity. The outbox is temporary Cloudflare storage, not Supabase, and is required for retry durability. Writes are idempotent using the event key; failed deliveries are retried and an owner-visible queue count signals backlog. The queue is not atomic with business D1 mutations: enqueue can fail after a business action, and an outage or unbounded backlog can exceed two minutes. Older queued records are retained until delivered; cleanup only covers rows in Postgres. If strict physical retention or guaranteed capture is required, additional queue expiry and reconciliation policies are needed. API calls are not all captured (idle QR polls and some health endpoints are intentionally excluded).

The old dashboard's 24h/7d/30d charts and filters use indexed Postgres data, with counts calculated for the selected period rather than just a loaded page. Prior-period comparisons and VPN classification are unavailable; CSV export and AI explanation are disabled in Supabase mode. Search scans the retained JSON and may become slow on a small project. Pagination is newest-ingested first. Free Supabase has limited capacity, may pause after inactivity and has no automatic backups; set usage alerts and arrange backups if needed. Keep 30-day quotas under observation. A successful repository test or a configuration change is not proof of production persistence.

The journal-specific names are `SUPABASE_JOURNAL_URL`, `SUPABASE_JOURNAL_PUBLISHABLE_KEY`, `SUPABASE_JOURNAL_SECRET_KEY`, and `SUPABASE_JOURNAL_JWKS_URL`. Only URL and secret key are used by the server-to-server RPC client; publishable key and JWKS URL are not required for this integration and are not used for authentication. `SUPABASE_JOURNAL_SECRET` remains a legacy fallback. Never put the secret in frontend variables or chat.

## Write efficiency and indexing

The encrypted outbox sends up to 25 events in a bounded batch (about 500 KB per RPC), rather than one HTTP request and transaction per event. Each event is still stored separately: audit history is not sampled or coalesced. The unique event key and `ON CONFLICT DO NOTHING` prevent retry updates and duplicate rows after a lost response. A rejected batch is retried individually to isolate bad records; outages and rate limits do not fan out. The queue is acknowledged only after Supabase confirms delivery. An older schema lacking the batch RPC falls back to the single-event RPC; apply the updated SQL before deployment to benefit from batching.

The existing indexes support kind/time charts, newest-ID pagination, retention deletion, and event-key deduplication. More indexes would add write amplification and storage; add them only after measuring real query plans. Unbounded substring searches still scan JSON. Physical sharding or time partitioning is not enabled: for this single small 30-day project it introduces migration, retention and global deduplication complexity, and is not justified without measured load. Monitor database size, egress, queue age/backlog, query latency and cron success before considering a tested partitioning migration. Batching lowers request and transaction overhead, not the number of distinct events stored, and cannot guarantee remaining within Free quotas.

## Diagnosing the outbox

The owner-only journal view shows a sanitized last transfer failure (configuration, credentials, missing schema, rejected event/schema, rate limit, decryption, or service). It contains no event, URL or key and remains visible while the queue is nonempty, including when the Worker configuration is invalid. The queue retries automatically; it does not prove every upstream event was captured. Check that `JOURNAL_ENCRYPTION_KEY` has not changed, install `supabase/journal.sql`, verify the URL and server-side secret, and confirm that a new test event reaches the dashboard and the queue drains. Never change the encryption key while events are pending. If the dashboard says no alarm is scheduled with entries pending, investigate the Durable Object alarm and storage errors before attempting repair; do not delete the object or its data.

### Diagnosing a reported missing function

The `schema` transfer category means an RPC returned HTTP 404, not proof that a function is missing. Confirm the Worker URL points to the intended active project and its Data API is enabled and exposes the `public` schema. In that project's SQL editor, check the expected functions and `service_role` privileges without sharing secrets or journal contents:

```sql
select p.proname, pg_get_function_identity_arguments(p.oid) as arguments,
       has_function_privilege('service_role', p.oid, 'EXECUTE') as service_role_can_execute
from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public' and p.proname in
  ('atlas_journal_ingest', 'atlas_journal_ingest_batch', 'atlas_journal_page')
order by p.proname;
```

If missing or mismatched, have the project administrator review and apply `supabase/journal.sql` in the **correct project**. It changes permissions and configures a retention cron that deletes journal rows older than 30 days, so verify that policy and pg_cron availability first. Check Supabase's API schema cache if functions exist but the API still returns 404. The batch endpoint alone may be absent during an upgrade: the buffer attempts the single-event endpoint. After correction, observe automatic retries and confirm the backlog decreases and a new event appears. Do not delete the queue, change its encryption key, or paste credentials into chat. The displayed count is capped at 100+, not an exact queue size.

## Historical migration preparation (not live)

`worker/lib/journalSupabaseBackfill.ts` is an isolated D1-to-Supabase building block, not an enabled job or route. It reads bounded ID pages up to a supplied high-water mark, filters on a fixed cutoff, uses stable source keys, and returns a cursor only after a batch acknowledgement. It never deletes source rows. It does not migrate R2, schedule jobs, persist checkpoints, verify the destination, or reconcile duplicates. A batch acknowledgement does not prove row content matches if a key already exists. No live migration has been run.

Before using it, build and test an operator-controlled runner and independent destination verification; inventory source formats, mutations, retention and the R2/D1 overlap. In particular, R2 shadow copies and D1 rows may represent the same event with different keys; blindly importing both could duplicate audit history. Use an immutable, unique source namespace, fixed snapshot/watermark and cutoff, account for writes around cutover and protect credentials and personal data. Verify completeness and duplicate policy in staging before any production import. Never delete source data without successful reconciliation and an approved retention/backup plan. The 30-day destination retention policy will exclude or remove older history.
