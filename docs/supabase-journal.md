# Supabase journal cutover (staged; not enabled by this change)

This implementation uses a dedicated Supabase project's Postgres as the primary store for new API and audit journal events. It does not write new Supabase-mode events to the journal R2 bucket or to the D1 journal tables. Existing R2 and D1 journal history is not imported or deleted. The Agent and product images still use their separate existing R2 storage. The legacy R2 pipeline remains available only for pre-cutover outbox items and rollback.

## Security and privacy

The Worker authenticates and authorizes journal viewers using existing owner/admin checks. Only the server sends the Supabase secret to the Data API; it must never be shipped to browsers, mobile apps, logs, source control, or chat. Use a dedicated Supabase project. `public.atlas_journal` has RLS enabled and no anon/authenticated table or RPC privileges; only the server-side service role can execute the two narrowly scoped functions. A Supabase secret key is powerful and bypasses RLS: protect it, rotate it on exposure, and do not reuse it outside the journal project. Do not enable automatic public table grants. Verify with Supabase's security advisor.

Journal records are stored as searchable JSON in Postgres, **not encrypted with the journal's application key at rest**. They can include usernames, IPs, user agents, and audit details. Supabase hosts the data in its selected region. Data sent to Supabase, their platform-side encryption, access controls and the project's privacy/compliance obligations are different from the previous application-encrypted R2 archive. The Durable Object outbox retains encrypted records in Cloudflare until acknowledged.

## Provision and test before activation

1. Create the dedicated Supabase project with Data API enabled and public auto-grants disabled. In its SQL editor run `supabase/journal.sql`. It creates the journal table, two service-role-only RPCs, indexes, and an hourly `pg_cron` cleanup job. If any SQL or scheduler step fails, **do not switch production**. Verify that `atlas-journal-retention` exists and runs successfully in the Supabase Cron dashboard. Reads exclude rows older than 30 days; the hourly cleanup can leave expired physical rows for up to an hour or longer if the job fails. Failed jobs must be monitored.
2. In Cloudflare Worker settings set **server-side secrets** `SUPABASE_JOURNAL_URL` (the `https://<project-ref>.supabase.co` Project URL) and `SUPABASE_JOURNAL_SECRET_KEY` (a server-only Supabase `sb_secret_...` key, or legacy `service_role` JWT). Do not use the publishable/anon key. Retain the current 32-byte base64 `JOURNAL_ENCRYPTION_KEY` and the `JOURNAL_BUFFER` binding: both are needed for the encrypted outbox and retries. Never change the key while entries are pending. No secrets should be pasted into chat or committed.
3. Deploy and verify the new code in an isolated non-production environment first, with `JOURNAL_ARCHIVE_MODE=supabase`, a dedicated test project, secret and buffer. Test audit and eligible API capture, queue drain, owner-only pages, period filters and charts, outages and retries, duplicate acknowledgment, RLS/anon denial, 30-day cleanup, and actual Supabase limits. Monitor 503s and the buffer health endpoint. The repository tests use mocked HTTP and local Postgres; they do **not** verify your live project, secrets, pg_cron, connectivity or deployment.
4. Before production cutover, drain the old R2 outbox to zero and verify it. Older queued events retain their original destination across mode changes; cutting over with a backlog could still write them to R2. Deploy the verified Worker with `JOURNAL_ARCHIVE_MODE` set to `supabase` in `wrangler.jsonc` (the current repository value deliberately remains `buffered`), and preserve the existing private R2 binding until the old backlog is empty. Check both journal types with real events and confirm chart counts and the cron job. Do not remove historical data or storage automatically.

Writes are idempotent using the event key; failed deliveries are retried and an owner-visible queue count signals backlog. The queue is not atomic with business D1 mutations: enqueue can fail after a business action, and an outage or unbounded backlog can exceed two minutes. Older queued records are retained until delivered; cleanup only covers rows in Postgres. If strict physical retention or guaranteed capture is required, additional queue expiry and reconciliation policies are needed. API calls are not all captured (idle QR polls and some health endpoints are intentionally excluded).

The old dashboard's 24h/7d/30d charts and filters use indexed Postgres data, with counts calculated for the selected period rather than just a loaded page. Prior-period comparisons and VPN classification are unavailable; CSV export and AI explanation are disabled in Supabase mode. Search scans the retained JSON and may become slow on a small project. Pagination is newest-ingested first. Free Supabase has limited capacity, may pause after inactivity and has no automatic backups; set usage alerts and arrange backups if needed. Keep 30-day quotas under observation. A successful repository test or a configuration change is not proof of production persistence.

The journal-specific names are `SUPABASE_JOURNAL_URL`, `SUPABASE_JOURNAL_PUBLISHABLE_KEY`, `SUPABASE_JOURNAL_SECRET_KEY`, and `SUPABASE_JOURNAL_JWKS_URL`. Only URL and secret key are used by the server-to-server RPC client; publishable key and JWKS URL are not required for this integration and are not used for authentication. `SUPABASE_JOURNAL_SECRET` remains a legacy fallback. Never put the secret in frontend variables or chat.
