# Localization roadmap and contributions

French is currently the source language; `src/i18n/messages.ts` contains each French source string together with its English and Arabic translations. The tuple format keeps translations together and is checked for missing values and duplicate keys. It is not yet an extensible language-pack system: `Lang`, language metadata, dictionary construction, the selector, native bridge and some locale-specific behavior currently assume three languages.

To contribute today, edit a tuple, preserve placeholders such as `{n}` and `{name}`, and run `npx vitest run src/__tests__/i18n-core.test.ts src/__tests__/whats-new.test.ts` and `npm run i18n:missing`. Review translations in context, especially amounts, plural forms, user data, and right-to-left screens. The static audit reports candidates, not a verified percentage: it also sees code, names and fragments, and cannot find every dynamic message.

## Future language packs

A practical next step is one source catalog and one JSON or similar catalog per language, with stable message IDs, language metadata (BCP-47 locale, direction and fallback), contributor documentation, and automated duplicate/placeholder/plural checks. Migrate existing French keys gradually with compatibility tests; don't rewrite or machine-translate customer data. Support a language only after the selector, persistence, Android bridge, date/number formatting, RTL behavior, screenshots and native-speaker review are ready. Splitting files alone does not add a language. Existing pattern matching and DOM translation need a compatible migration rather than a simple file split.

For community translations, [Weblate](https://docs.weblate.org/en/latest/admin/continuous.html) supports GitHub synchronization and community workflows; [Crowdin](https://support.crowdin.com/developer/dev-tools/) offers GitHub Actions and translation pull requests. Either can work with standard catalog formats once chosen. Compare hosting, cost, access controls, contributor experience and data policies before adoption. Machine translation can suggest drafts, but human review is necessary, especially for financial terminology and RTL. Do not send business or customer data to translation providers without an appropriate privacy review and authorization.

## Recommended provider

Use **Weblate** as the preferred community-localization platform: it is open source, supports GitHub-based review and common JSON catalogs, and can be hosted or self-hosted. This is a recommendation, not a claim that it is the most-used provider, and no project or synchronization is configured yet. Before enabling it, agree on hosting and review permissions, migrate to a supported catalog format with round-trip tests, and configure translation changes to go through reviewed pull requests rather than directly overwriting production strings. Do not configure GitHub credentials or enable automatic machine translation without approval.

## Finding missed strings

Run `npm run i18n:scan` for the advisory TypeScript-AST scan (or `npm run i18n:scan -- --file PhoneHome --limit 200`; use `--json` for a complete machine-readable list). It examines JSX text, common visible/accessibility attributes, simple conditional literals, and selected notification/error calls, comparing them against the existing French-source catalog. This adapts the AST-based approach used by tools such as [eslint-plugin-i18next](https://github.com/edvardchen/eslint-plugin-i18next) to our existing DOM translation bridge; a generic no-literal rule would flag translated French source text. `explicit-required` marks SVG, which the bridge intentionally skips. Check each result in context: component props, split text and catalog matches may still be misleading. The scan does not resolve variables, concatenations, all template literals, API content or every UI surface; passing it does not prove translation coverage.

The isolated visual-review workflow also saves `i18n-observations.json` with heuristic French clues in rendered English and Arabic demo pages, after the normal readiness wait. It is supplementary, not a test or coverage metric: names, loanwords and already-correct text can be false positives, while the vocabulary heuristic and unopened states miss other issues. It intentionally avoids form values, marked user data and code, but can still include demo data that is not marked; **run it only against the isolated demo, not real customer accounts**. Review screenshots, dialogs and accessibility labels manually. Pseudolocalization and native-speaker checks would improve future testing but are not implemented.

For bidirectional text, follow [W3C guidance](https://www.w3.org/International/docs/bp-html-bidi/): set direction with HTML, use `dir="auto"` or `<bdi>` for unknown-direction user text, prefer CSS logical properties, and isolate mixed numeric runs instead of reversing digits. Test amounts, negative numbers and currency ordering in context. Browser screenshots are useful but do not replace physical-device keyboard and screen-reader checks.
