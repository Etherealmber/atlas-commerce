# Localization roadmap and contributions

French is the source language. `src/i18n/catalogs/fr.json` maps normalized French source strings to themselves; `en.json` and `ar.json` contain the matching translations. `src/i18n/messages.ts` loads these catalogs into the existing runtime bridge: changing a target JSON value changes the app. Missing values fall back to French at runtime, but the catalog guard rejects missing entries before merge. French text is currently the identifier: changing it requires updating all three files, and changes lose translation history unless carefully mapped. Do not put customer data in catalogs.

Thank you to everyone who translates and improves Atlas Commerce! Contributors can improve existing translations, not only add missing ones. Review proposed translations with a native speaker and in context, especially financial terminology, plural forms, accessible labels, variables and RTL. Keep each placeholder, including repeated occurrences such as `{n}` and `{name}`. Run `npm run i18n:validate`, `node --test scripts/i18n-validate.test.mjs`, `npx vitest run src/__tests__/i18n-core.test.ts src/__tests__/whats-new.test.ts`, and `npm run i18n:scan`. The structural guard does not validate meaning or prove that screens are translated.

## Crowdin community setup (owner action required)

This repository is prepared for Crowdin; **no Crowdin project or integration has been created or connected**. The linked translate-web-pages project is an example, not an Atlas project. Follow [Crowdin GitHub integration](https://support.crowdin.com/github-integration/) instructions and the current plan's permissions and limits:

1. Create an Atlas Commerce project under an account you control. Set French as source, English and Arabic as target languages. Choose public community access, contribution/review permissions, moderation, project visibility and privacy policies as appropriate. Allow contributors to suggest improvements to existing translations and reviewers to approve them.
2. Merge the catalog preparation and `crowdin.yml` into the source branch first. In GitHub, check whether `translation` already exists and who owns it. If absent, create it from the intended source branch; if present, inspect its history and coordinate with its owner rather than resetting or overwriting it. Configure Crowdin's GitHub integration to read the source branch and deliver translations to `translation`, with automatic PR creation disabled if supported. Never sync directly to production. Verify current integration settings against Crowdin's documentation, as options and branch behavior can change.
3. Import the existing English and Arabic JSON translations **once** into the matching Crowdin languages; confirm they appear for editing. Do not repeatedly reimport GitHub translations over community edits. Confirm the `%two_letters_code%` mapping resolves to `en` and `ar` in a small test before enabling synchronization. Restrict the project to these languages until app support is implemented. Configure export to include existing translations and preserve every key; run the guard on downloaded catalogs. If export omits unapproved translations or missing entries, do not merge the incomplete export. Choose review/approval policy deliberately.
4. Test one harmless edit end-to-end: source upload → edit/review in Crowdin → export to `translation` → inspect diff and CI → owner opens a PR to the intended base. Check that no source catalog, unrelated files, branch history or credentials were changed. Ensure the integration's GitHub permissions are limited to the repository and required branch. Avoid simultaneously configuring Crowdin's GitHub app and a separate scheduled action, which can race and overwrite changes.
5. Publish the actual project link in the application/docs only after setup and verification. Thank contributors in release notes and on the About page; ask permission before publishing names or handles and respect pseudonyms.

`crowdin.yml` contains no credentials. Do not commit tokens, use a third-party project, or enable machine translation/AI processing without a privacy review and authorization. An integration or service account needs owner authorization; the prepared config alone does not publish a branch or open PRs. The `translation` branch should be maintained by the owner/integration, not force-pushed. Crowdin is a practical GitHub-friendly community option, not a guarantee of translation quality. See also the [official Crowdin action](https://github.com/crowdin/github-action) for an alternative to the GitHub app.

## Supporting more languages

Separate catalogs alone do not add a language: `Lang`, metadata, selector, persistence, native bridge, formatting, direction and fallbacks still assume FR/EN/AR. Add each with tests and contextual native-speaker review before advertising it. Prefer stable message IDs and proper plural handling in a future migration, while preserving existing runtime compatibility.

## Finding missed strings

Run `npm run i18n:scan` for the advisory TypeScript-AST scan (or `npm run i18n:scan -- --file PhoneHome --limit 200`; use `--json` for a complete machine-readable list). It examines JSX text, common visible/accessibility attributes, simple conditional literals, and selected notification/error calls, comparing them against the existing French-source catalog. This adapts the AST-based approach used by tools such as [eslint-plugin-i18next](https://github.com/edvardchen/eslint-plugin-i18next) to our existing DOM translation bridge; a generic no-literal rule would flag translated French source text. `explicit-required` marks SVG, which the bridge intentionally skips. Check each result in context: component props, split text and catalog matches may still be misleading. The scan does not resolve variables, concatenations, all template literals, API content or every UI surface; passing it does not prove translation coverage.

The isolated visual-review workflow also saves `i18n-observations.json` with heuristic French clues in rendered English and Arabic demo pages, after the normal readiness wait. It is supplementary, not a test or coverage metric: names, loanwords and already-correct text can be false positives, while the vocabulary heuristic and unopened states miss other issues. It intentionally avoids form values, marked user data and code, but can still include demo data that is not marked; **run it only against the isolated demo, not real customer accounts**. Review screenshots, dialogs and accessibility labels manually. Pseudolocalization and native-speaker checks would improve future testing but are not implemented.

For bidirectional text, follow [W3C guidance](https://www.w3.org/International/docs/bp-html-bidi/): set direction with HTML, use `dir="auto"` or `<bdi>` for unknown-direction user text, prefer CSS logical properties, and isolate mixed numeric runs instead of reversing digits. Test amounts, negative numbers and currency ordering in context. Browser screenshots are useful but do not replace physical-device keyboard and screen-reader checks.

## Arabic plural and bidirectional preparation

`src/i18n/plural.ts` provides an explicit `Intl.PluralRules`-based selector, using each language's runtime CLDR categories. Arabic requires `zero`, `one`, `two`, `few`, `many`, and `other`; French and English categories come from `resolvedOptions()`. It requires a nonempty form for every category supported by the runtime and replaces `{n}` with a locale-formatted number; Arabic numeric runs are isolated, not reversed. Tests exercise 0, 1, 2, 3–10, 11–99, 100, 101, 103, 111 and a fraction. This is infrastructure only: existing `{n}` strings do not automatically gain Arabic plural grammar, and no new plural catalogs or translations have been published. Before using it in a screen, define message-specific, translator-reviewed forms, add a Crowdin-compatible representation and checks, test placeholders and provide a safe French fallback. Do not invent Arabic forms or use English rules for Arabic.

For RTL, use markup direction and isolate dynamic values using `<bdi dir="auto">`; use `dir="ltr"` for known left-to-right identifiers such as IP addresses and timestamps. Prefer CSS logical properties, mirror directional navigation selectively and never reverse digits. Review keyboard focus, screen readers, amounts and mixed-language text on mobile and desktop. References: [Unicode CLDR plural rules](https://cldr.unicode.org/index/cldr-spec/plural-rules), [MDN Intl.PluralRules](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/PluralRules), and [W3C bidi HTML guidance](https://www.w3.org/International/docs/bp-html-bidi/).
