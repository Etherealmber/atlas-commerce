# Atlas Desktop native password + OTP: audit and production preparation plan

**Status:** work in progress, not approved for production. PR #192 supplies a staging-only test pilot, not a production method. No deployment, release, merge, real-provider validation, or Windows test is authorized by this plan. This repository does not contain the Rust client. The normal website login must not change. Preserve existing account data and pilot records; use additive, versioned schemas with explicit migration and rollback. Do not enable a production route merely by removing a staging check.

## Audit of the merged PR #192 baseline

- Discovery (`worker/routes/desktopNativeDiscovery.ts`) exposes password/OTP only if every pilot gate and the exact HTTPS origin are configured. `/pilot` operations and the standalone embedded challenge document require staging, so the production Worker does not offer them by default. The browser choice remains explicit. The [current pilot contract](desktop-native-auth-v2-client.md) specifies its endpoints and WebView navigation.
- The page submits Turnstile to the server; the native client polls with state and PKCE verifier. The server validates Siteverify success, hostname, action and transaction cdata; expiration, cancellation and single-use status are checked. It requires the creating and completing IPs to match. This neither prevents shared-NAT relay nor proves device or user identity. VPNs, multi-homing and address rotation can cause rejection. No provider or real WebView validation is implied by simulated tests.
- Login is deliberately limited to a named non-owner account, one configured test inbox and PBKDF2-100000 hashes. Account existence and invalid credentials return the same response envelope and perform a dummy PBKDF2, but identical timing and delivery patterns are not guaranteed. The website has owner-secret handling, legacy hashes, account roles, editable user email, and company/mailbox fallback. An `app_users.email` is editable, not proven to be controlled by its user; using it directly as a second factor would be unsafe. The checked-in `EMAIL` binding is restricted to one destination, and the normal website mail flow has distinct fallbacks. Neither is a production multi-account delivery policy for this new route.
- Persistent pilot limits and OTP attempt caps exist, but fixed windows have boundary bursts, account bucket saturation can deny a victim, and broad cross-channel credential-stuffing, mail-spam and recovery policy need a deliberate review. Fake and eligible accounts need comparable external responses; rate-limit decisions must not depend on existence. HMAC OTPs and single-use checks must stay separate from the website's legacy OTP records.
- Pilot sessions have hashed random bearer tokens, 15-minute access and 12-hour absolute refresh expiry, rotation, immediately-previous-token replay revocation, and account change/delete triggers. They are bound to origin and account, **not cryptographically to a device**. Older refresh-token generations are not tracked; a copied bearer is usable elsewhere. Lost refresh responses require restart; a logout with a lost response may not revoke the server session. These are production blockers, not device attestation.

## Concrete sequence and acceptance gates

1. **Policy and prerequisites.** Define an explicit eligible-account rule preserving active status and existing roles, including a reviewed decision for the separately configured owner and legacy password hashes; no silent role promotion or changes to website login. Establish a separately verified account-specific OTP address: enrollment/change must require existing authenticated authorization plus out-of-band proof of mailbox control, invalidate outstanding native OTPs and sessions on change, and never fall back to a shared inbox. Add non-enumerating recovery for missing/inaccessible addresses, with operator identity checks and audit; do not accept client-supplied recipient. Require a provider binding capable of delivering to those addresses, domain/sender authorization, deliverability and secret-safe logs. Existing raw `email` and current single-destination binding do not satisfy this gate.
2. **Separate, off-by-default production protocol.** Design a versioned contract and additive tables independent of pilot names and data, with a separate explicit production flag, canonical origin allowlist, dedicated OTP MAC key and email transport. Absence/misconfiguration must advertise unavailable and fail closed. Never weaken hostname, action, cdata, PKCE, expiry, comparison or atomic consumption; never create a bypass during provider outage. Perform generic-response and latency/distribution tests for nonexistent, ineligible, bad-password and eligible accounts without claiming mathematically constant timing. Add persistent, atomic global/IP/account/pair password, OTP and delivery budgets across relevant channels; bound queues and retention, monitor account-targeted denial of service, and document recovery and Retry-After.
3. **Device-bound sessions and recovery.** Specify a per-installation non-exportable signing key, proof of possession on token issuance, refresh, logout and authenticated requests, with request method, canonical URI, origin, body digest, server nonce and freshness/replay binding. A random fingerprint is only a label. Create atomic, versioned device/session enrollment and explicit user/admin device revocation; bind tokens to account, exact origin and key. Track all rotated refresh generations for the entire family lifetime; atomically rotate both tokens and revoke on reuse, concurrent reuse and account/role/password/OTP-address change. Specify a single writer and OS-vault atomic update; uncertain responses require reauthentication and server-side revocation capability, not retry. Confirm all existing auth gates validate proof rather than only a bearer. A deployable key enrollment/revocation system is not implemented by a policy or a fingerprint.
4. **Challenge and client.** Keep the WebView challenge-only with no bridge or secret inspection; provider submission remains server verified. Explicit browser fallback creates a new request and compares the code. Validate every navigation/redirect against exact origin and path, allow only necessary provider child frames, enforce HTTPS and CSP. Maintain single in-flight poll, bounded interval and lifetime, and fail closed for cancellation, replay, lost response or network changes. Retain same-IP until an independently reviewed alternative exists; document false denials and shared-IP/relay risk. Evaluate phishing-resistant authentication, abuse monitoring and independent risk acceptance before any production rollout.
5. **Verification and operations.** Add contract tests and transactional races for eligibility, generic failures, enrollment, OTP mail/expiry/attempts, challenge races, key proof/replay, rotation across generations, logout, disablement and rollback; regression test existing website login. Validate real D1 primary consistency, email, Turnstile, browser security headers and Windows WebView2 separately in an isolated environment. Provide least-privilege secret management, retention, secret-free counters/alerts and reviewed WAF/APM/proxy redaction; establish emergency flag-off, session-family revocation, secret rotation and rollback without deleting existing accounts. Flag-off alone must not be represented as permanent revocation.
6. **Approval gate.** Publish exact implemented client wire contract only after design and implementation agree. Keep production unavailable pending independent security review, real-provider and Windows results, recovery/operations readiness, and explicit owner approval. No deploy, merge or release as part of this work. Rust must implement the native fields, CSPRNG state/verifier, challenge WebView controls, proof-bound polling, explicit fallback, device key/proofs and secure session persistence. No passkey or production-readiness claim follows from this plan.

## Work in this branch

- **Implemented, staging pilot only:** atomic refresh rotation now records hashes of consumed generations in a separate expiry-indexed table. Reusing a recorded generation revokes the family; concurrent refresh/logout with the last known token can revoke it even if a refresh response is lost. A per-family fixed-window limit of eight refresh attempts per ten minutes bounds churn; logout remains possible. No raw tokens are stored. The old `previous_refresh_hash` is preserved into history on the first upgraded rotation. Tokens consumed before the immediately previous one are unknowable; mixed old/new Worker versions can also create unrecorded history. This is not cryptographic device binding or a complete production session lifecycle.
- **Implemented, staging pilot only:** password and OTP verification use the existing website persistent account/IP budgets across channels, in addition to the pilot-specific budgets. Unverified challenges cannot consume the shared password budget. This necessarily affects website throttling at the abuse threshold, but not its UI or normal successful-login flow. Fixed-window bursts, targeted account exhaustion and shared-IP denials remain possible. Storage failures fail closed. Challenge and recovery limits are not unified across channels.
- **Implemented but not wired:** an adapter-gated mailbox enrollment core with account-bound pending/verified state, expiring single-use HMAC proofs and old-address notification/change proof. No real authorization, delivery, recovery or login integration is configured; see [enrollment options](desktop-native-enrollment-options.md). Staging desktop creation has an additional shared IP budget across v1 and v2.
- **Still not implemented:** externally accessible multi-account verified OTP enrollment/delivery and recovery, comprehensive cross-channel challenge/recovery controls, device possession proof/enrollment/revocation, production endpoints/discovery/flags, production monitoring and operational revocation tooling. The pilot remains single-account, single-test-mailbox, disabled by default and staging-only. Do not use it as a production workaround. The website login is unchanged.
- **Rollout/rollback of this incremental staging change:** use a genuinely isolated Worker and D1; leave existing flags off until the isolated test is intended. The additive history table is initialized only on pilot login/session operations. Existing accounts, tokens and pilot rows are not migrated or deleted. For rollback, disable both pilot flags, revoke any remaining pilot families in the isolated database, and revert the Worker; flag-off alone only suspends sessions. Do not rely on a downgrade to recognize history or on staged flags for production. Preserve the table for incident analysis according to the test environment's retention policy; deletion must be separately authorized. Never share the preview's production resources. Real D1 transaction/rollback behavior and deployed log redaction remain unverified.
- **Rust today:** follow the [staging contract](desktop-native-auth-v2-client.md), including one in-flight refresh, vault-atomic token replacement, no automatic retry after uncertainty and best-effort logout with the last known refresh. No device-key protocol is offered yet. Implementing device binding requires a new reviewed contract, not a fabricated fingerprint or client-only check.

Further changes, real-provider/Windows validation and all approval gates above remain necessary; the plan is not an authorization to enable or deploy.

## Implemented tests (local simulation)

SQLite/D1 simulation covers replay across generations, preservation of the immediately previous legacy generation, atomic history rollback, concurrent refresh/logout, family churn limits, shared password/OTP budgets, unverified challenge admission, and failure-closed limiter storage. See the test report in the PR for current counts. These tests do not validate the deployed D1 service, real mail or Turnstile, Windows WebView2, or deployed monitoring/redaction.
