# Native mailbox enrollment and recovery: decisions for review

**No production enrollment, recovery or mailbox-verification HTTP API is exposed.** The application still uses the staging-only test-account pilot. The new `desktop-mailbox-enrollment.ts` is an unwired building block exercised with injected test adapters, not an authorization policy or a mail service. Current `app_users.email` is editable and is never imported as verified. The existing website login and email behavior are unchanged.

## Implemented building block and integration boundary

`createMailboxEnrollment(db,key,adapters)` returns `null` unless a D1-like transactional binding, a dedicated MAC key of at least 32 characters, an `authorize` callback and a `send` callback are supplied. Key length is not proof of entropy: use an independently generated secret from a secret store. Nothing registers or calls the module in the Worker. No release flag can enable it. Until a real adapter is approved and wired, delivery is unavailable; tests use a fake sender.

The caller adapter must validate an **existing** active account session and explicit fresh reauthentication separately for both start and confirm, derive `userId` from that trusted session (never caller-supplied IDs), use a primary database session, enforce a policy-approved first-enrollment/recovery decision, and fail closed on error. The existing `checkConfirmPassword` is insufficient as-is because it accepts an omitted password. No owner account (which has no `app_users` row), administrator override, or recovery is implicitly permitted. The adapter's standalone authorization check does not close a concurrent session-revocation or reauthentication-expiry race: integration must bind the commit transaction to the still-valid session and reauthentication evidence in authoritative storage. Before exposing any route, enforce HTTPS, exact Origin/port and CSRF protections, a bounded strict body and operation deadlines, generic errors, and secret-free logs. The adapter must never trust a native fingerprint, raw role or user claim. Detailed route paths and public schemas are **not yet implemented**.

The core provides separate additive tables for an existing account's active verified address and one pending request. An authenticated caller can propose a candidate address, but it is **untrusted until verified** and is never used by existing website login. The code preserves local-part spelling, normalizes the domain, and accepts a deliberately narrow ASCII address grammar; internationalized addresses need a reviewed policy. On first enrollment it delivers a six-digit CSPRNG code to the candidate; on an active verified-address change it sends a notice **and** separate code to the old address and another code to the candidate. Both codes, session and reauthentication are needed to complete a change. A send timeout is five seconds per delivery; any failure, timeout or account-change race fails closed. Adapters must honor `AbortSignal` where possible; a late delivery can never activate a failed request. A code is bound to its random request ID and purpose by a dedicated HMAC key, expires after ten minutes, is not stored in plaintext, and has at most five attempts. A transaction consumes the pending request and inserts/replaces the verified record once; concurrent completion has one winner. A lost success response does not reissue an authorization. There is no mail retry: restart after an expired/failed request, subject to budgets. Bounded cleanup runs only on another start and cannot guarantee timely deletion during idle periods.

Account username, password hash/salt, role, active state or editable email change cancels in-flight enrollment and suspends the factor; restore/re-enable does not restore it. Deletion suspends it as well. A suspended factor cannot be replaced by this module: approved recovery is required. Retained addresses are sensitive data and need an approved deletion/retention policy. These triggers affect only new mailbox tables, not old account data, and are created only if the unwired service is invoked. Other future native OTP/session tables must be transactionally invalidated on verified-factor change; this building block is **not wired** to pilot or future login/session issuance.

Once the trusted actor is known, `start` reserves the existing cross-channel password budget and `confirm` the existing cross-channel OTP budget: 60/IP/minute, 300/IP/10 minutes, 20/account/10 minutes combined and five/account+IP+purpose/10 minutes; reservations persist and failures consume budget. A verified logged-in actor can exhaust its own account's capacity and shared-IP users can still collide. The `send` callback is reached only after authorization and limiting, and only one nonexpired request/account can be sending/pending. Production recovery and delivery must share reviewed account/network and global quotas across channels; none is exposed here. Pseudonymous hashes of names/IPs remain dictionary-guessable.

## Decisions: first enrollment (choose a policy)

**Option A — existing strong session + explicit password reauthentication + new-mailbox code.** Easier bootstrap and self-service, but anyone who has stolen the current session and password can enroll their own mailbox; an editable email or proof at the new mailbox alone is not independent identity proof. Requires an actual strict reauth implementation and account notification.

**Option B — existing session + approved administrator/out-of-band identity check, then new-mailbox code.** Harder for a remote password thief but introduces administrator insider risk, help-desk delay, secure record-keeping and potential social engineering. A dual-control or delay-and-notify variation can reduce unilateral administrative takeover but has availability and staffing costs.

The core enforces only whatever approved `authorize` adapter actually verifies; it does not choose A or B. Decide whether old verified mail must always confirm changes (the present core requires it), what notice to send, and what to do when no old address exists. The separately configured owner requires its own stable identity and authorization adapter; do not map it to an invented `app_users` record.

## Decisions: lost mailbox / device recovery (choose a policy)

**Option A — recovery through a second already enrolled, phishing-resistant factor or another approved trusted device**, with fresh proof, audit, notification and optional delay. This avoids unilateral administrator reset but cannot recover users who have lost every factor, and device keys must first be implemented and securely enrolled.

**Option B — staffed administrator recovery with identity verification, dual approval where feasible, notification to prior channels and a cooling-off window**, followed by revocation of all existing native factors and sessions and re-enrollment. This works when all devices are lost but puts exceptional power and responsibility on operators and may exclude organizations with no independent second approver.

For **owner/administrator recovery**, either use pre-enrolled offline recovery material (stored separately, single-use, protected and periodically tested) or an independently verified multi-person administrative process with documented break-glass control. The former can be lost/copied and needs lifecycle management; the latter depends on available trustworthy operators and formal identity checks. Neither is implemented. Decide who approves, required evidence, delay, notifications, revocation scope and how to prevent a recovery request from disclosing whether an account exists. Do not silently use a shared company inbox or editable email.

## Abuse, observable behavior and deployment

Public login and future recovery must use generic envelopes/statuses across nonexistent, disabled, unverified, wrong-password and delivery-failed accounts; do not report mailbox existence or destination. Generic bodies do not eliminate statistical timing, mailbox notification, quota or side-channel differences. Include credential-work equalization, end-to-end statistical testing, delivery caps, abuse monitoring and a recovery path resistant to targeted lockout. Expose retry timing conservatively. Edge source IP must come from a trusted proxy; never trust arbitrary forwarded headers. Fixed windows admit boundary bursts and shared-NAT false denials, while distributed attackers can exhaust an account bucket; monitor aggregate counts without account/IP labels and choose non-disclosing mitigation.

The staging pilot's challenge creation now shares an additional fixed IP budget of eight creations/five minutes across desktop v1, v2 phone and pilot when the staging challenge flag is explicitly enabled. Existing per-channel caps still apply; website login is not charged by this additional budget. This is not a production or all-channel challenge/recovery defense. See [the pilot contract](desktop-native-auth-v2-client.md) and [the device proof proposal](desktop-native-device-key-proposal.md). Real provider, D1 transactions, log redaction and Windows WebView2 remain unvalidated.
