# Agent history: proposed Supabase cutover — not enabled

Decision: use **separate Agent tables in the existing journal Supabase project**, do not copy legacy R2 conversations, retain new conversations for 30 days of inactivity, and store Agent images separately as encrypted R2 objects with the same retention. Do not mix chat data with `atlas_journal`; the Agent lifecycle is independent of the audit/API journal. Existing journal outbox, secrets, encryption key and retention must remain untouched. Current code still stores Agent snapshots and model transcripts in R2; this document is a plan, not a production migration.

## Compatibility and safety gates

- Preserve the existing authenticated `/api/admin/agent/threads` list/detail/PUT/DELETE shapes, version acknowledgements and conflict semantics. The current desktop accepts only `storage: r2`; it must be updated together with the Worker. Chat and stream endpoints also use a separate R2 transcript and must move at the same time, including the native Android contract. The mobile web currently stores history on-device; changing its server storage alone does not synchronize or expire its local cache. Audit Android's actual released client and test its supported versions before deployment; repository web tests cannot prove APK compatibility.
- Start with an empty namespace: do not read/import legacy R2 chat or inadvertently upload old browser snapshots as new conversations. Legacy browser/mobile caches need an explicit versioned reset and must not silently recreate old conversations. Existing R2 objects remain physically present until a separate, verified cleanup; do not delete them as an incidental side effect of deployment.
- Use stable, collision-resistant account identities, never the current lossy username sanitization. Restrict backend access to server-only credentials, enforce account-scoped operations, RLS and least-privilege privileges. Assess that a shared project/secret shares failure domain and trust with journals; monitor Free plan storage, rate limits and project availability.
- Design transactional versioned writes with conflict detection and deletion tombstones; prevent a stale client or in-flight chat reply from resurrecting a deleted/expired thread. Treat unknown write acknowledgements and retries as idempotent operations. Fail closed on Supabase errors; do not claim a save or deletion succeeded before confirmation.
- Store image bytes encrypted with a dedicated stable server secret and unique random nonces; validate media and size, authorize all access through the Worker, keep R2 objects private, and never put secret keys or public object URLs in clients. Keep only opaque image references in Supabase. Implement durable, retryable deletion of images on explicit deletion and expiry, accounting for in-flight uploads and crashes. Avoid logging or exposing user data. Decide how encrypted image keys are rotated and restored before deployment.
- Define inactivity as the server timestamp of the last successful user interaction, not history-list reads. Reads must filter expired threads. Cleanup must be scheduled, monitored, idempotent and race-safe; physical deletion may lag if a scheduler or R2 is unavailable. Establish and test how browser/Android caches expire and how offline devices behave. Include all images and model transcripts in deletion.
- Test auth/isolation, CAS conflicts, duplicate requests, client disconnection, stale saves, deletes, expiry races, Supabase/R2 outages, partial cleanup recovery, key loss, pagination, quotas, and native Android compatibility in staging. Validate live Supabase Data API permissions and schedules before cutover. Measure API latency and reduce round trips without skipping fresh reads or truthful error handling.

Thirty days of inactivity can be a sensible privacy/storage trade-off, but it is not a backup policy and may surprise users. Explain the policy in the interface before enabling it. Supabase Free can pause or exhaust limits; a shared project outage would affect both Agent and journals. No guarantee of physical deletion or Android compatibility exists until the implementation and staging checks above are complete.

## Android code review (preparation only)

Reviewed `Etherealmber/atlas-commerce-android` main at commit `7c10e1eab68b40f5003f612a6ad6e211c9b60386`, not a running APK. Its `AtlasApi.kt` calls the same thread list/detail/PUT/DELETE and chat/stream endpoints. The `PutAgentThreadRequest` has only title and messages: it does **not** send `expected_version`, and `AgentThreadDetailDto` does not expose the response metadata version. `AgentViewModel` persists snapshots repeatedly and retries failures. Therefore a backend requiring mandatory CAS without a compatibility strategy will break existing Android saves, while unconditional legacy writes can overwrite concurrent edits or resurrect deleted chats. An Android update with version handling and explicit conflict/deletion behavior is recommended for safe synchronization, followed by real versioned APK testing; preserving endpoints alone is not proof of compatibility. The repository defines a delete call, but a search of the Agent screen/view model did not find a corresponding deletion action.

Android's saved message DTO contains role, text and duration, not image data; images are passed to the chat request separately. Future encrypted image persistence cannot rely solely on the Android thread snapshot. Verify attachment restore, expiration and deletion using a real Android build and the planned server-managed attachment protocol. The local mobile-web deletion added in this PR is not a native Android change.

An isolated AES-GCM payload-envelope prototype exists in `experiments/agent-storage/crypto.ts`; it is **not wired into the Worker**, does not read any secret or Supabase, and does not store images. It requires independent security review, key lifecycle/rotation design and Worker compatibility testing before use. The prepared SQL intentionally grants no API permissions and has no retention scheduler. Do not enable a cutover from this prototype.

### Current prototype limitations

The draft now includes a bounded, account-filtered metadata list and a server-side adapter for encrypted get/conditional put. The draft list returns bounded encrypted title/count summaries in one call, which the adapter decrypts; it has not yet been integrated with the UI or tested in live Supabase. The adapter currently hashes the exact username to isolate accounts; this avoids lossy R2-name collisions but is **not** a stable immutable identity across renames and is not secret against username guessing. Choose and test a stable server-side account identifier before enabling. The list does not refresh the inactivity timestamp; read filtering does not physically delete rows. The deletion function only creates a tombstone and does not yet delete images. The list/get/put/tombstone routes can use the adapter in isolated test mode or when a production Worker is explicitly configured with `AGENT_HISTORY_STORAGE=supabase`. Demo is excluded. The production opt-in is not enabled in the checked-in configuration. This preview rejects image payloads and legacy unversioned writes. Chat uses Supabase transcripts only when a parent snapshot already exists; legacy transcript browsing and bulk deletion are disabled in preview. It is not ready for real conversations or deployment. A separate Worker cron now schedules a bounded cleanup pass every 15 minutes when Supabase Agent mode is selected, but it is not running in production and these draft functions have not been applied to your project.

### Image prototype (not enabled)

`experiments/agent-storage/images.ts` stores a bounded image as an AES-GCM envelope under an account/thread-scoped R2 prefix, authenticating the image ID as well as the account and thread. Tests cover ciphertext isolation, malformed input, bounded batches and retry after R2 failure. It does not itself enforce private bucket configuration or authorize reads; callers must do both. It has isolated preview-only upload and retrieval routes, but no scheduled job, production configuration or snapshot/chat attachment integration. Its batch deletion must only run after a durable tombstone and a writer-fencing protocol: a concurrent or delayed upload can otherwise create an orphan after the final empty listing. The draft SQL now creates a durable queue atomically with deletion and bounded expiry; claims have leases and stale acknowledgements are rejected. An isolated runner deletes image batches and can acknowledge completion only when the database confirms there are no unresolved upload intents; this is safe only once every upload path uses the fence. Upload race fencing, authorization, crash recovery and real R2 testing remain required before deletion or 30-day retention can be claimed. The preview rejects image data in snapshots and chat; its separate image routes are not yet called by clients.


### Upload fencing prototype (not enabled)

The draft now records an upload intent while locking the active conversation before any R2 PUT. Tombstones use the same row lock. A known-completed PUT racing a tombstone is deleted before its intent is released; cleanup completion is blocked while intents exist. Unknown or interrupted PUT outcomes deliberately remain pending indefinitely rather than being assumed safe. The experimental runner can acknowledge an empty prefix only through the database check for unresolved upload intents; it is invoked by a separate 15-minute Worker cron only when Supabase Agent mode is selected; it must not run against real data until all writers use the fence. A safe recovery strategy for unresolved uploads, true concurrent database/R2 tests, queue integration and authorization are required before production; Installing the SQL does not activate these jobs; review permissions and validate the exact project before installation. Do not enable cleanup in production until recovery is resolved.

### Model transcript prototype (not enabled)

The draft now has separately encrypted model transcripts and independent compare-and-swap revisions. Parent tombstones and expiry remove the transcript in the same database transaction, and writes require an active parent. The adapter has no legacy R2 fallback. Local PGlite tests exercise isolation, stale writes, deletion and expiry. Buffered and streamed chat use the transcript adapter in isolated preview and fail if the parent snapshot does not yet exist. Streaming emits an error if persistence conflicts, even if tokens were already sent. Current clients can send a first chat before creating a snapshot, and end-to-end first-turn coordination, retry idempotency and live testing are still needed. This prototype is not a live migration. Installing the schema does not enable chat or perform any migration.

The isolated adapter now includes a create-only first-turn parent helper that handles a concurrent creator without overwriting an existing snapshot or resurrecting tombstones. It is deliberately not wired to chat because it can race a client that read an empty version; first-turn coordination and idempotency remain unresolved.

The desktop preview now creates an empty, versioned parent before its first model call and retains that version for the later snapshot save; a conflict stops the model call. The same path is selected for explicit production Supabase mode. Mobile web now performs a versioned first-turn save; native Android coordination still needs verification.

`src/mobile/agentPreviewSync.ts` tests the intended mobile-web first-turn snapshot/CAS flow, including refusal to republish local-only history. PhoneApp now negotiates storage mode before loading the local cache, and uses this helper only in Supabase modes. A versioned user snapshot must be acknowledged before chat; the assistant reply is saved with the next version. Failures are surfaced rather than silently overwriting. Legacy Workers that omit the capability field retain legacy behavior. This remains partial: the mobile history list is local-only, remote hydration and expiry/offline handling are incomplete, and interrupted reply persistence is not yet durably reconciled.

Desktop preview hydration now uses separate local message/pending namespaces and an authoritative server list, with tests ensuring legacy cached messages are not uploaded when the preview history is empty. This is not a complete cache migration: legacy desktop messages and history are hidden until the corresponding server response identifies storage mode, including on discovery failure; active thread IDs, expiry/offline handling, account identity collisions and mobile/Android caches still require a proper pre-hydration mode/epoch protocol. Do not enable production on the basis of these tests.

The cleanup prototype now includes a Worker-side RPC queue adapter and local end-to-end SQL/fake-R2 tests. It retries when an upload intent is unresolved, so interrupted/unknown writes can still block cleanup indefinitely. This is not a recovery solution, and the scheduler is not deployed or enabled for this mode.


The preview-only image routes derive the account from the authenticated Worker session, use bounded request bodies, encrypt before R2, check the parent on reads, and return private no-store responses. A thread deletion reports `image_cleanup_pending`; physical removal requires the not-yet-scheduled cleanup worker. Local PGlite/fake-R2 tests cover account isolation and deletion. These routes do not prove bucket privacy or real-service behavior, do not resolve uncertain writes, and are not wired to the Agent composer or Android.


### Production-mode wiring (not enabled)

A production Worker can now select `AGENT_HISTORY_STORAGE=supabase` explicitly; that branch fails closed if Supabase or its encryption key is unavailable, does not read or write legacy R2 transcripts/snapshots, and skips the legacy R2 conversation age purge. A separate 15-minute cron can run the bounded Agent cleanup queue when selected, without rerunning daily finance jobs. The owner reports that the SQL schema/RPCs were applied and passed the read-only readiness check and rollback probe; the separate Agent encryption key is not confirmed, and the mode is **not set in wrangler configuration**. It must not be treated as a completed cutover: current Android/mobile may send an unversioned snapshot or chat before a parent exists, attachments are not wired from the composer, unknown image writes can block cleanup forever, and live deployment and private bucket behavior remain unverified. Do not enable this mode until these gaps are resolved. Schema installation alone does not activate the mode.

`GET /api/assist/status` now advertises the configured Agent-history mode, version requirement, retention policy and whether the image API is experimental. The response is marked no-store so clients can negotiate the mode rather than infer it from a failed write. It reports configuration, not live Supabase health or proof that cleanup has completed. Mobile web negotiates this capability; native Android integration is not verified. Older Workers may omit it.

The 15-minute cleanup trigger is configured but not deployed. It handles bounded batches, so actual physical deletion may be delayed by backlog, errors, or unresolved upload intents. This cadence is not a 30-day deletion guarantee; cron delivery, queue capacity, and real R2/Supabase behavior need live monitoring and verification. The existing daily business jobs are routed separately.

Mobile-web first-turn integration has local UI tests for mode negotiation, no legacy-cache import, save-before-chat, conflict rejection and a visible unconfirmed-reply warning. It has not been verified against the deployed Worker or a real Android APK. Never enable production on this change alone.

The SQL installer aborts instead of dropping a pre-existing four-argument `atlas_agent_put` overload. If it aborts, stop and inspect that function; do not delete it automatically. The installer creates restricted RPCs and tables and modifies Agent-table privileges, but does not schedule or invoke cleanup, import chats, or enable storage mode. Inspect the exact project and back up schema before installation. The read-only `supabase/agent-readiness-check.sql` reports expected objects and selected role grants; it does not audit all custom roles, actual API connectivity, encryption keys, or R2.

The project owner reported installing the schema and shared readiness-check results showing all four tables and eleven RPCs present with expected RLS, search path, and anon/authenticated/service-role privilege flags. This is user-reported SQL-editor evidence, not proof of actual PostgREST connectivity or Worker encryption-key configuration. `supabase/agent-transaction-probe.sql` performs synthetic RPC assertions in a transaction that rolls back; it does not test encryption, API roles through PostgREST, Cloudflare, R2, or production traffic. It must be run as a complete script, including its final rollback.

Mobile web now lists up to 20 server conversations in Supabase mode and can view their text read-only without replacing the current draft. This is not editable server-history hydration, pagination, attachment restore, or offline reconciliation; the separately shown device-local cache can still contain stale data. The owner also reports that the rollback-only SQL probe succeeded on the live project.

Mobile text-only synchronization now refuses snapshots containing richer message fields rather than stripping desktop metadata or images on a subsequent save. `reconcilePhoneReply` is a tested building block for a lost snapshot acknowledgement: it rereads the server, accepts an already-identical saved reply, or retries only against the exact recorded base version and content. It does not call the model. It is **not yet wired to the UI or a durable, account-scoped recovery record** and does not recover replies lost before a record can be saved. No process-death or live-service guarantees are established.

The branch adds an owner/admin-triggered Settings diagnostic (`POST /api/admin/agent-storage-probe`). It checks the configured Agent key with a local AES-GCM round-trip and performs a read-only Supabase RPC using a random synthetic account; it does not create records, enable storage, expose credentials, test writes, validate an old key, or prove R2 cleanup. It is unavailable in demo and requires a valid authenticated privileged session. This diagnostic has only been tested locally and cannot be used in production until a reviewed Worker containing it is deployed. Never rotate an existing Agent or journal encryption key merely to make a diagnostic pass.
