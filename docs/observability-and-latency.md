# Worker observability and latency investigation

The supplied request list shows multiple authenticated API requests started close together and finishing in about 5–6 seconds, while the QR polling and mobile preferences requests finished faster. This does not establish where time was spent: inspect Cloudflare request traces and browser timing (queueing, connection, TTFB and response) for the same time window before attributing it to D1, KV, authentication, the network or a cold start. Web requests perform revocation and device checks; authenticated requests without a bookmark use a primary D1 session. Do not bypass these security checks or loosen consistency merely to improve latency.

Settings previously requested categories, units, admin users, admin configuration and the audit log on initial mount, in addition to settings and profile/security calls. These now load when the relevant tab is first opened, remain in component state when switching tabs, and support normal refresh/mutation flows. A fresh, in-memory, session-scoped settings GET cache makes reopening immediate during its 60-second TTL; a first visit or expired cache still requires a request. The cache is not persisted across reloads and does not share entries across tokens. Failed first loads must not expose editable fake defaults. Nested panels can still fetch when remounted, and explicit refreshes, changed audit filters and writes can trigger requests.

The repository previously enabled persisted Workers Logs **and** Traces at 100% head sampling, with invocation logs on. Each invocation and its spans can increase observability ingestion; the application also has a separate D1 API journal that writes most API requests asynchronously. These are different systems and quotas. The config alone does **not** prove which account limit was hit, its billing window, or which worker generated the usage. In this change traces are sampled at 5% while logs remain at 100%; this reduces expected trace volume, not necessarily overall log usage. Head sampling may miss a slow request or error trace. This setting takes effect only after deployment; it does not reset an already-exhausted quota. [Cloudflare's tracing documentation](https://developers.cloudflare.com/workers/observability/traces/) describes independent head sampling and its tradeoffs.

To verify production: in Cloudflare Observability/usage, identify the specific exhausted metric, account, plan and period, and break ingestion down by worker, event type and route. Compare log and trace volume before/after deployment; check D1 reads/writes and the separate `api_log` volume too. For a representative slow authenticated request, compare its total request time to auth, D1 and KV spans if sampled; compare primary/replica location and browser timing. The screenshot is not sufficient to establish causality or claim a measured speedup. Avoid storing tokens, query strings, customer data or full URLs when collecting diagnostic examples.
