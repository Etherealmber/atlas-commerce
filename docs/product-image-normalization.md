# Product image normalization

Product image uploads are converted in the Worker before R2 storage. JPEG, PNG, static or animated GIF (first frame only), and WebP are decoded based on their bytes, EXIF orientation is applied (including mirrored orientations), and the oriented image is center-cropped to a square. Images are downscaled without enlargement to a maximum **768 × 768 pixels** using Lanczos, then encoded as WebP at quality **82**. Alpha is retained. Re-encoding strips EXIF, GPS, ICC, and other original metadata. The R2 object has `Content-Type: image/webp`, an immutable `.webp` URL, and a normalization marker; catalog-image responses expose `content_type: image/webp` for normalized images.

For Worker memory safety, input is limited to 4 MiB encoded, 4 million pixels, and 4096 pixels per source dimension. Image-bearing JSON requests are limited to 6 MiB, including streaming requests without `Content-Length`. Larger photos must be reduced by the client before upload. Image decoding and WebP encoding use Worker CPU and memory; confirm the deployed Worker plan and limits are sufficient before enabling bulk conversion. Invalid, corrupt, unsupported, or oversized images are rejected rather than stored as images; unavailable storage returns an error. Existing non-image assets, such as logos and signatures, keep their existing behavior.

Product/catalog upload, replacement, direct product `image_url` changes, and mobile product-request image uploads go through this path. Inputs can be image data URLs or existing objects in the configured R2 bucket under `products/`, `pending/mobile/`, or `product-requests/`. The Worker does not fetch arbitrary external URLs: **new or changed external image URLs are rejected**, including URLs that older versions accepted. Existing external URLs, objects outside those prefixes, missing objects and malformed files remain unchanged and are reported for manual review/re-upload. An unchanged legacy URL on an unrelated product edit is not rewritten automatically.

## Existing product images

After deploying the Worker, an environment-owner session can run the bounded `POST /api/admin/product-images/normalize` endpoint repeatedly. No remote migration is run automatically by this change. Take a D1 and R2 backup first. The endpoint checks the verified owner account, reads only the primary D1 and configured R2 bucket, and processes at most five records per call. It scans two phases in order:

1. `{ "phase": "images", "after": 0, "limit": 3 }` for `product_images`.
2. `{ "phase": "products", "after": 0, "limit": 3 }` for standalone `products.image_url` and variant references.

For each response use `data.next_after` as the next `after` for the same phase until it is `null`; then start the other phase at zero. The response reports `updated`, `unchanged`, `failed`, and per-row `{id, code}` failures. A full final page may require one extra empty request. Failures advance the cursor: resolve them and rerun both phases from zero. The endpoint never logs or returns original image data. Requests need the usual Bearer session and device fingerprint header, if that session requires it. For example, a trusted operator may set `ATLAS_URL`, `ATLAS_SESSION`, and optionally `ATLAS_FINGERPRINT` in their shell, then use `scripts/normalize-product-images.mjs`; never put a token in source control or share it in chat. The script refuses plain HTTP except localhost, never prints the token, and exits nonzero if records need attention.

The migration writes a new immutable object first, then uses conditional D1 updates in a batch for the image row and the matching product's primary URL. IDs, product associations, ordering, alt text, and primary flags are preserved; concurrent edits are reported as `CONFLICT` rather than overwritten. A content-addressed key and R2 metadata marker prevent recompression on reruns. The migration itself retains original objects, and normalized objects are not automatically deleted when an image/product is removed, because products and variants may share them. **Existing deletion paths can still delete shared legacy objects**; avoid deleting products or legacy images while migrating and check remaining references before any cleanup. This can leave orphaned objects; use a separately audited reference-aware cleanup and a backup before deleting any object. Existing cache invalidation is best-effort and cross-isolate visibility can be delayed.
