# Atlas desktop authentication defaults and integration conflicts

This records the user's proposed defaults as the design direction. It is **not an implementation, security review or authorization to activate production**. Apart from the disabled read-only discovery described below, there is no v3 route. Existing v2 remains a staging-only bearer-token pilot; ordinary web login is unchanged.

## Implemented discovery contract

`GET /api/auth/desktop/v3/capabilities` is public, requires HTTPS, accepts no query string, and rejects an `Origin` header unless it exactly equals the request origin including port. It never returns account or configuration information; `Cache-Control`, `CDN-Cache-Control` are `no-store` and `Referrer-Policy` is `no-referrer`.

```json
{"success":true,"data":{"version":3,"enabled":false,"reason":"NOT_READY","methods":{"password_otp":{"available":false},"mailbox_enrollment":{"available":false},"recovery":{"available":false},"device_proof":{"available":false}},"browser_fallback":{"version":1,"capabilities_path":"/api/auth/desktop/v1/capabilities","automatic":false}}}
```

HTTP 400 uses `{"success":false,"code":"HTTPS_REQUIRED","error":"HTTPS requis."}` for HTTP, or `{"success":false,"code":"INVALID_REQUEST","error":"Requête invalide."}` for query/wrong Origin. No flag can currently enable v3; setting `DESKTOP_NATIVE_V3_ENABLED=true` is **not** a switch and has no effect. A future, explicitly disabled-by-default gate needs a separate implementation once every essential route is ready. The fallback advertises the existing separately gated v1 capability, not a promise that browser approval is available. Rust must check that capability and get explicit user consent before starting a fresh v1 request and comparing codes. Never automatically fall back or infer native support from flags, runtime, user agent, fingerprint or this discovery response.

## Defaults now selected for design, not yet enforceable

- Regular secondary accounts: an authenticated session, explicit nonempty password reauthentication and proof at the proposed individual mailbox. This does not protect against an attacker possessing both the session and password; new-mail proof establishes control, not independent identity. Notify the user and audit security changes; use only verified notification channels, not editable `app_users.email` as ownership evidence.
- Owner and admin: stronger separately reviewed enrollment; never silently treat an admin as a regular user or map the configured owner to a fabricated `app_users` record. Specific control and approver remain to be selected. The present mailbox core stores only `app_users` IDs and does not support the configured owner.
- Lost mailbox/device: prefer another enrolled strong factor or device; otherwise require verified administrator assistance, notice, an appropriate delay and revocation of affected devices/sessions. A regular web fingerprint or `trusted_devices` row is not a strong factor. Require independent control over approvals; do not allow a recovery requester to approve their own request. Exact identity evidence, approver roles/quorum, delay and cancellation/appeal still need operational approval. If there is no independent administrator or verified contact, fail closed rather than inventing evidence.
- Owner: pre-enrolled single-use offline recovery codes **plus** a separately controlled break-glass process. Specify offline-code issuance, one-time atomic use and replacement, separate controller identity, evidence and authority, revocation, delay, notification and auditing before implementation. The configured sole owner is not a separate controller for their own break-glass. No such codes or controller exist today.
- Prefer hardware-protected device keys. With explicit disclosure and protected platform storage, software keys are permitted; fail closed if required storage is unavailable. A platform-provider name, non-exportability claim or public-key signature proves no hardware attestation. Require actual verified attestation and its trust/revocation policy before making hardware assertions.

## Conflicts to resolve before wiring

1. Web `stock-auth-v2` tokens are deterministic from account material/IP/fingerprint; they carry no independent session identifier or expiry. Voluntary web logout marks trusted-device resume and does **not** invalidate the token. Checking the existing session and password therefore cannot establish the required revocable, fresh session or atomically exclude a concurrent logout. Changing ordinary web login/logout semantics was not authorized. A separate short-lived, server-tracked enrollment reauthentication grant with a reviewed binding to a genuinely revocable authenticated session is needed; a second `authFailReason` check followed by a write is not atomic.
2. `checkConfirmPassword` intentionally accepts an empty password and cannot provide the required explicit reauthentication. A strict verifier must share the web credential admission budget, reject omitted credentials and prevent account changes/session revocation racing its commit. `trusted_devices` is revocable by fingerprint but is not proof of a hardware key, possession or independent identity; legacy `none` fingerprints have no row to bind.
3. Current `writeAudit` catches all errors and is best-effort; it cannot promise a durable, atomic security audit. Build a transactional secret-free audit/outbox with retention, delivery monitoring and incident response. Current `app_users.email` may be changed without verification; it cannot become a trusted recipient by migration or act as the independent notification channel. First-enrollment notification when there is no prior verified address needs a chosen independent route.
4. A proposed administrator could be able to modify accounts/passwords; authorization to recover must be explicitly defined and separately controlled. The owner is configured by secrets rather than an `app_users` row, including no existing stable owner factor/session ID. Recovery and account disablement must revoke all related DPoP device keys and families atomically. `desktop-mailbox-enrollment.ts` does not yet invalidate those future sessions and no recovery implementation exists.
5. The dedicated Resend adapter is connected only to the unwired core factory; real Worker authorization and OTP login do not call it. It needs verified-domain configuration, limited secret credentials, provider delivery/bounce and redaction checks. Provider acceptance is not proof of delivery. One-account staging delivery does not prove arbitrary-recipient readiness.
6. The proof verifier has no atomic nonce/JTI store or resource-gate enforcement. A proof can currently be verified repeatedly. Implement DPoP nonce issuance, replay retention, signed request binding, account/device enrollment, access/refresh family binding and revocation in the same authoritative transaction as each protected operation. Cover every Worker authorization entry point including report/print ticket paths; protect the new protocol from bearer/query-token downgrade. Simulated SQLite is not proof of D1 behavior.
7. Existing shared budgets are fixed-window and can cause account-targeted denial and shared-IP false rejection; v3 recovery, delivery and challenge creation aren't fully covered. Implement comprehensive shared abuse control, generic errors and statistical timing/side-channel tests. Generic errors cannot hide email delivery, network or notification behavior; same-IP relay remains possible. No credentials, OTPs, tokens, proof verifiers, sensitive URLs or mail content in application, edge, analytics, crash or provider logs.

## Client and operational requirements

The [staging client contract](desktop-native-auth-v2-client.md) provides exact existing v2 pilot schemas, deadlines, navigation and explicit-browser handoff. [The cross-platform audit](desktop-native-cross-platform-audit.md) specifies required Rust work for Windows CNG/WebView2/DPAPI, macOS SecKey/WKWebView/Keychain and Linux WebKitGTK/Secret Service/optional hardware. The [candidate proof profile](desktop-native-device-key-proposal.md) is not an executable v3 contract and must be versioned/reviewed with a Rust implementation before use. Native controls hold password and OTP; only the temporary challenge page communicates the Turnstile token directly to the backend. No DOM, storage, cookie, script or network-body inspection or JS bridge. Users explicitly select browser fallback, with a fresh request and code comparison.

A future release needs tested protected atomic token-pair storage, cross-process refresh serialization, no unsafe retry after a lost response, session/device emergency revocation, account-mutation invalidation, secret-free monitoring and rollback that does not resurrect old tokens. Test on real Windows 10/11, macOS, Linux, their actual WebView/provider combinations, Cloudflare Siteverify, D1, mail delivery and log pipeline; CI/simulated SQLite/Node results alone do not establish compatibility. Do not deploy or activate from this draft PR.
