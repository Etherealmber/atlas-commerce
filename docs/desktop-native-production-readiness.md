# Native Desktop production readiness: engineering record

**Not production-ready. No production native password/OTP protocol is implemented or advertised.** This is a reviewable engineering record, not permission to deploy or evidence of independent security review. The only implemented native password/OTP path is the [staging pilot contract](desktop-native-auth-v2-client.md). It retains its named test account, fixed test mailbox, two staging flags, HTTPS origin and server-side Turnstile validation. There is no hidden production switch to turn on. The normal website login and its UI have not been replaced.

## Account and mailbox decisions required

The existing authority is `app_users` for secondary accounts and separately configured owner credentials; existing user and administrative profile routes can edit `app_users.email`, and it has no proof-of-control bit. The existing email binding is configured for one destination; normal website login has separate account/company/configured-inbox fallbacks. These are not safe evidence of an independently verified native-login factor. Merely sending a code to a newly edited address must not automatically establish production eligibility.

A proposed policy for owner review is: an authenticated, active account reauthenticates with its current credential, initiates enrollment to its existing account-specific address, and proves control with a CSPRNG code delivered directly to that address. Store only a keyed code digest; limit lifetime, attempts, sends and concurrent attempts, and use atomic single-use transitions. Bind the verified record to stable account ID and exact normalized address. Never use a client-supplied recipient or company/shared-mailbox fallback. Changes to email, disablement, deletion, password, role or recovery state must atomically invalidate relevant enrollment challenges and native sessions; returning an old address or re-enabling an account must not resurrect trust. Successful delivery is not proof of mailbox control. A transport failure leaves the challenge unusable and public login responses remain generic. Do not include an OTP in links, logs, failure payloads or native URLs. Initial enrollment, address changes, administrator recovery and emergency revocation need audited, authenticated workflows that are distinct from public login. This is a **proposal**, not implemented.

The owner must decide and document before implementation/enablement:

1. **Bootstrap and recovery:** what independent evidence authorizes the first enrollment, replacement after loss of the old mailbox, and administrator-initiated recovery? Is reauthentication plus proof at the new address sufficient initially? Who can approve recovery, what notice/cooling-off is required, and how are recovery decisions audited? Allowing an administrator who can edit email or reset passwords to redirect an OTP is a material account-takeover policy decision, not a technical proof of the user.
2. **Accounts and roles:** how the separately configured owner account enrolls and recovers, and whether legacy/unsupported hashes must be reset before native enrollment. No role should be silently elevated or a live account modified by migration. No existing email is automatically grandfathered as verified.
3. **Mail:** select and configure an appropriately scoped transport that actually delivers to all verified account mailboxes, sender/domain authorization, rate limits, secret-safe telemetry, retention and operational ownership. The existing destination-restricted binding is insufficient. Decide whether shared mailboxes are forbidden and how that is enforced; mailbox proof alone does not prove individual identity.

Until these choices and workflows are implemented and independently reviewed, the single-account test restriction is intentionally **not** removed. Public generic responses cannot hide email delivery, account-holder notifications, timing or rate-budget side channels perfectly. Native client errors must not reveal whether the account, verified mailbox or delivery exists.

## Device and session security — design gate, not an implemented protocol

A device label, fingerprint, IP, Turnstile result, and locally generated public key are not hardware attestation or user identity. The current pilot issues ordinary bearer access and refresh tokens, partitioned by exact origin and account but usable if stolen. It does not enforce a device key, and Rust must not label it device-bound.

A candidate design is an independently reviewed, asymmetric proof-of-possession scheme such as standards-based DPoP with a per-installation signing key. Bind a newly enrolled public-key thumbprint to the account, origin, request and resulting session only after the complete password and mailbox OTP flow. Require verified proof for issuance, each refresh and logout, and **every** authenticated business request, not just the refresh endpoint. Proof must bind the method and canonical target URI, server nonce, unique proof ID, time window and access-token hash; establish atomic replay detection across Worker isolates and enforce nonce and clock-skew rules. Reject algorithm confusion, private key material in requests, invalid curves/encodings, key substitution, reused proofs and wrong origins. Avoid using a custom ad-hoc signing serialization without review. The applicable standard does not automatically bind arbitrary request bodies or provide hardware attestation; determine whether additional body binding, streaming uploads and proxies are required before finalizing the protocol.

The Rust implementation would generate a signing key inside an OS-protected, non-exportable key container; send only the public key and signed proofs; persist a reference to that key and tokens separately in the OS vault; and never export the private key to the WebView. Exact APIs, curves, encodings, hardware/OS support and handling of software-backed keys must be selected and interoperability-tested. A copied key container or compromised local process may still be able to sign. Do not claim possession proves a particular person or an uncompromised device.

Required decisions: supported Windows versions and whether TPM-backed keys are mandatory or software-protected keys acceptable; exact proof standard/algorithm and endpoint compatibility; how a user adds a replacement device; how keys are revoked by the user and administrators; and identity verification for lost-key or lost-mailbox recovery. Review existing UI/role permissions before exposing those actions. Token-exchange and proof schemas are deliberately **not published as executable endpoints** until the design is finalized and independently reviewed. Once specified, a versioned production capability must advertise exact schemas separately from `/pilot`; it must fail closed if any dependency is absent.

## Session lifecycle implemented in the staging pilot

A successful OTP yields `{token_type,access_token,refresh_token,access_expires_at,session_expires_at,origin,username,role}`. Store the pair **atomically**, encrypted at rest in an OS vault isolated by exact scheme/host/effective port and account; protect against concurrent processes refreshing the same pair. Access lifetime is at most 15 minutes, absolute family lifetime 12 hours. `POST /pilot/session/refresh` with `{origin,refresh_token}` returns both replacements atomically; the old access token is invalidated. A current or recorded consumed refresh can be presented to `/pilot/session/logout` to revoke, not recover, its family. A failed or uncertain refresh must not be replayed; attempt logout with the last locally held refresh, clear the vault and reauthenticate. If logout is lost or unavailable, server-side revocation is not guaranteed. OTP-response loss can leave an orphan family until expiry or authorized operator revocation.

For rotations performed by the updated Worker, D1 atomically records the consumed refresh hash and updates both token hashes. Reuse of any recorded generation revokes the family, including an old-token logout racing a refresh. The old immediately-previous hash is imported at the first updated rotation. Earlier historical hashes and any missed during mixed-version deployment cannot be reconstructed. The limit of eight refresh attempts/family/ten-minute fixed window, including failed downstream attempts, bounds generation churn; a 12-hour family can intersect up to 73 windows (584 newly consumed generations, plus at most one imported generation). Fixed windows allow boundary bursts. Bounded cleanup deletes expired history in batches when new pilot requests are created; without traffic rows may persist, and the total number of families is not globally storage-bounded. A cleanup scheduler/retention policy and quota analysis remain required. Retaining a hash lets anyone holding that old bearer revoke the family: a denial-of-service tradeoff. Account mutation/delete triggers revoke existing pilot families; a previously authorized request can still complete. Disabling flags suspends, but does not permanently revoke, sessions.

## Challenge, limits and residual risks

The implemented staging discovery and exact request/response, errors, deadlines, CSP and WebView2 rules are in the [pilot client contract](desktop-native-auth-v2-client.md). The desktop creates independent CSPRNG state and PKCE S256 verifier, chooses `embedded_webview`, loads the standalone page with only a request reference, and polls server status with its proof. The page, not Rust, submits the Turnstile result. The backend checks Siteverify success, hostname, action and cdata and atomically enforces expiry, cancellation and single use. If explicitly selected, system browser uses a **new** request with a pairing-code comparison; there is no silent fallback. The desktop must not inspect WebView cookies, DOM, scripts, storage, network bodies or provider token, nor inject scripts or create a bridge.

The staging password/OTP endpoints also reserve the existing website's shared durable account/IP counters once a challenge is verified. At exhaustion, website and native can throttle one another; fixed windows, shared NATs, distributed spraying, account-targeted denial of service and email side channels remain. Unknown names consume the same counter structure; hashed low-entropy names/IPs are pseudonymous rather than anonymous. The pilot's challenge and recovery protections are not a unified cross-channel production defense. Same-IP binding fails across VPN/multi-homed networks and does not stop same-NAT or social-engineered challenge relay. Siteverify and a fingerprint do not identify the person; OTP/email is phishable. Wall-clock skew is not used by the embedded page as expiry authority; the server uses its clock and Rust must use a bounded monotonic deadline.

## Rollout and rollback checklist (future only)

- [ ] Implement and independently review verified enrollment, recovery, account policy, device proof on all routes, unified abuse controls, monitoring and a separately versioned production contract. Do not point the pilot at production or reinterpret its flags as production flags.
- [ ] Use a genuinely isolated test Worker, D1, mail transport, Turnstile keys and accounts. The checked-in preview shares production resources and is not suitable for this purpose. Verify fresh-profile service-worker isolation, exact HTTPS origin and nonstandard port, iframe rules, CSP, provider redirects and actual interactive and noninteractive challenges in WebView2 and the explicit browser flow.
- [ ] Prepare additive migrations and backup/restore procedures on copies of representative data. Validate transaction and primary consistency on real D1, migration of old sessions, triggers, cleanup, retention, capacity, rollback, partial failures and mixed-version deployment. Never delete or rewrite existing account data merely to enable native login.
- [ ] Provision distinct high-entropy OTP MAC and other protocol secrets through the deployment secret store, restrict access, set rotation/revocation procedures, validate sender/domain ownership and provider delivery quotas. Do not place secrets in repository vars or CI logs.
- [ ] Validate Worker/edge/WAF/proxy/APM/client/mail logs and crash reports using synthetic non-secret markers. Disable URL/query, header, body, token, OTP, username, email, IP and provider-response capture for auth flows. Use aggregate, low-cardinality counts, latency histograms and alerts for challenge failure, abuse denial, mail failures, revocation and cleanup; no secrets or account-identifying labels. Alert fatigue and shared-IP account lockouts need an operator runbook.
- [ ] Establish monitored flag-off, permanent device/family revocation, compromised-secret rotation, lost-response recovery and operator authorization. Flag-off alone does not permanently revoke sessions. Rollback must prevent old Worker versions from accepting revoked/rotated families; revoke affected families before rollback. Verify that no existing web session or account is deleted or rewritten.
- [ ] Test real Turnstile and mail failures, expired/replayed requests, D1 outages and concurrent calls on the isolated environment; test real WebView2 on supported Windows versions and runtimes. Mock tests do not demonstrate those integrations. Complete independent security review, user risk acceptance and explicit deployment approval before any production activation.
